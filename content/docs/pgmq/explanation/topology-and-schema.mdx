There are two different layers of setup in pgmq-hs: installing the pgmq schema
and creating application queue topology.

## Schema installation

The schema is the database implementation of pgmq itself: functions such as
`pgmq.send`, `pgmq.read`, `pgmq.archive`, topic routing functions, and the
tables those functions manage. You can get that schema by installing the pgmq
PostgreSQL extension, or by running `pgmq-migration`.

`pgmq-migration` 0.4 vendors the pgmq 1.11.0 schema and exposes a native component:

```haskell
pgmqMigrations :: Either DefinitionError MigrationComponent
```

The application composes it with every other component in one `pg-migrate` plan and owns the
deployment runner. That runner takes connection settings and acquires its own advisory-lock
connection; the runtime pool is not the migration connection. Fresh databases apply the PGMQ
baseline and native canary. Databases managed by the removed `hasql-migration` runner first import
one supported, verified predecessor history shape; the import records evidence without replaying
schema DDL. See
[Migrations](/docs/pgmq/reference/migrations).

## Queue topology

Topology is the set of application queues and queue features:

- standard, unlogged, or partitioned queue creation
- insert notifications
- FIFO indexes
- topic pattern bindings

You can create these directly with `pgmq-hasql`, but most applications should
prefer `pgmq-config` for boot-time reconciliation:

```haskell
ensureQueues :: [QueueConfig] -> Session ()
ensureQueuesReport :: [QueueConfig] -> Session [ReconcileAction]
```

## Reconciliation: create, report, and one mutation

`pgmq-config` snapshots existing queues, topic bindings, notification throttles,
and FIFO indexes with four read-only queries before mutating anything. It then
creates missing objects and reports skipped ones. It does not remove queues,
disable notify, remove old topic bindings, or change an existing queue's kind.

The one exception is the notification throttle interval. If a declared interval
differs from the stored one, the row is updated in place and reported as
`UpdatedNotifyThrottle`. The asymmetry is worth stating, because a queue's type
is also a "declared value disagrees with stored value" case and is *not*
repaired:

- The throttle interval has a **non-destructive in-place update** in pgmq's own
  API — `pgmq.update_notify_insert` rewrites one column of one row. Nothing is
  lost. Meanwhile a declared interval the reconciler silently ignores is a
  straightforward lie: the whole point of putting the value in the config is
  that changing it changes behavior.
- A queue's type has **no such update**. Converting between standard, unlogged,
  and partitioned means dropping the queue and recreating it, which destroys
  every message it holds. A process that runs automatically at startup,
  potentially on several replicas at once, must never do that — the failure mode
  is silent, unrecoverable data loss triggered by a one-word config edit. So the
  drift is surfaced as `DetectedQueueTypeDrift`, with both the declared and
  observed shapes, and a human decides.

The general rule: **reconcile automatically only where the repair is
non-destructive and the API supports it in place; otherwise report and stop.**

This makes it safe to call on every boot, but it also means destructive topology
changes should be modeled as explicit migrations or operator actions.

<Callout type="info">
  `UpdatedNotifyThrottle` and `DetectedQueueTypeDrift` shipped in 0.5.0.0. On 0.4.0.1 a changed
  throttle interval is silently ignored and reported as `SkippedNotify`.
</Callout>

## FIFO and topics are opt-in

FIFO uses the `x-pgmq-group` header and grouped read functions. It does not
require a special queue type, but production consumers should create the FIFO
index for performance.

Topics use bindings from topic patterns to queues. A topic send can deliver one
message to zero, one, or many queues depending on pattern matches. This is
publish-subscribe routing inside pgmq, not a separate broker.

## Choose the smallest setup that matches the workload

Use a standard queue for durable background work. Use an unlogged queue only
when losing queued work on crash is acceptable. Use a partitioned queue when the
queue is large enough that retention and partition maintenance matter. Add FIFO
only for per-group ordering, and add topics only when multiple queues should
receive messages by routing key.
