---
title: "Handle transient errors"
description: "Classify pgmq-effectful runtime errors before retrying."
---

```haskell
import Effectful (runEff)
import Effectful.Error.Static (runErrorNoCallStack)
import Hasql.Pool qualified as Pool
import Pgmq.Effectful

runWithRetryDecision ::
  Pool.Pool ->
  Eff '[Pgmq, Error PgmqRuntimeError, IOE] a ->
  IO ()
runWithRetryDecision pool program = do
  result <-
    runEff
      . runErrorNoCallStack @PgmqRuntimeError
      . runPgmq pool
      $ program
  case result of
    Right _ -> pure ()
    Left err
      | isTransient err -> putStrLn "transient failure: check operation safety before a bounded retry"
      | otherwise -> putStrLn ("permanent pgmq failure: " <> show err)
```

`isTransient` is conservative: pool acquisition timeouts, network connection
errors, unknown libpq connection errors, and session connection drops are
retryable. Authentication, compatibility, missing-type, and driver errors are
not.

## Server errors are classified by SQLSTATE

A statement error carrying a *server* error is retryable when its SQLSTATE is
`40001` (serialization failure), `40P01` (deadlock), `55P03` (lock timeout),
`57P01`/`57P02`/`57P03` (admin shutdown, crash shutdown, cannot connect now), or
anything in class `53` (insufficient resources). Every other statement error,
including decode and row-count mismatches, is permanent.

That whitelist applies to the published 0.6.1.1 package. The unreleased classifier below adds
receive-side lost-reply handling; it does not make arbitrary decode failures retryable.

A retry is only safe if the operation is idempotent. `sendMessage` retried after
an ambiguous failure can enqueue the job twice; prefer a dedupe key in the
payload or accept at-least-once delivery downstream.

## Lost replies in unreleased source

The reviewed source exports `isAmbiguousReply`; published 0.6.1.1 does not.
For that source version, choose the retry action in this order:

1. Check `isAmbiguousReply`. If true, record that the operation may have committed.
2. For operations that can duplicate effects, reconcile by a durable application key before retrying.
   Alternatively, use an idempotent design. Do not assume PGMQ deduplicates arbitrary sends.
3. Check `isTransient` for service recovery. Use a finite attempt count, backoff, and an overall
   application deadline for retry orchestration. The package does not add a call deadline here.
4. Keep ambiguity in the retry state. A later connection failure does not prove that the first send
   failed before commit. The pool may need another attempt to evict the dead connection.
5. Stop on permanent errors and return the unresolved outcome when the retry budget ends.

The helper recognizes empty-SQLSTATE statement/script errors and the exact driver extra-result
shape. Read the [classifier contract](/docs/pgmq/reference/effectful-api#unreleased-disconnect-classification).
It does not classify every network symptom or `DriverSessionError` as retryable.
