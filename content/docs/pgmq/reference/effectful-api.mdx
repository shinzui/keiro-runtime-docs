---
title: "Effectful API"
description: "The Pgmq dynamic effect, interpreters, runtime errors, and OpenTelemetry helpers from pgmq-effectful."
---

`pgmq-effectful` lifts pgmq-hasql sessions into an `effectful` dynamic effect.
Application code calls smart constructors under a `Pgmq :> es` constraint, and
an interpreter supplies the `hasql-pool` backend.

## Effect and operations

```haskell
data Pgmq :: Effect
type instance DispatchOf Pgmq = Dynamic
```

The public smart constructors mirror the Hasql sessions: queue creation, notify
configuration, FIFO index creation, send/read/archive/delete, visibility-timeout
changes, FIFO grouped reads, topic binding and topic sends, notification
throttle inspection, `listQueues`, and queue metrics.

<Callout type="warn">
  **Breaking since `0.5.0.0`:** the single-message visibility-timeout
  operations return `Maybe Message`, matching the session layer.

  ```haskell
  changeVisibilityTimeout :: (Pgmq :> es) => VisibilityTimeoutQuery -> Eff es (Maybe Message)
  setVisibilityTimeoutAt  :: (Pgmq :> es) => VisibilityTimeoutAtQuery -> Eff es (Maybe Message)
  ```

  `Nothing` means the message no longer exists — already deleted, archived, or
  popped — rather than an infrastructure failure. The `Pgmq` effect constructors
  `ChangeVisibilityTimeout` and `SetVisibilityTimeoutAt` change with them, so a
  hand-written interpreter must be updated. The batch variants are unaffected.

  The same release adds `listQueuesUnvalidated :: Eff es [UnvalidatedQueue]` and
  `listFifoIndexQueueNames :: Eff es [Text]` alongside `listQueues`.
</Callout>

<Callout type="info">
  In 0.6.1, `Pgmq.Effectful` re-exports all six FIFO operations: standard/polling variants of
  `readGrouped`, `readGroupedRoundRobin`, and PGMQ 1.12's strict-head `readGroupedHead`. It also
  exports `createPartitionedQueueWithPremake` for PGMQ 1.13.
</Callout>

## Plain interpreter

```haskell
runPgmq ::
  (IOE :> es, Error PgmqRuntimeError :> es) =>
  Pool ->
  Eff (Pgmq : es) a ->
  Eff es a
```

`runPgmq` executes each operation with `Hasql.Pool.use`. Runtime failures are
thrown through `Error PgmqRuntimeError`.

```haskell
data PgmqRuntimeError
  = PgmqAcquisitionTimeout
  | PgmqConnectionError HasqlErrors.ConnectionError
  | PgmqSessionError HasqlErrors.SessionError

fromUsageError :: UsageError -> PgmqRuntimeError
isTransient :: PgmqRuntimeError -> Bool
```

`isTransient` returns `True` for pool acquisition timeouts, networking
connection errors, uncategorized libpq connection errors, and session-level
connection drops. Authentication failures, compatibility errors, missing types,
and driver errors are permanent.

`OtherConnectionError` is classed transient despite hasql's documentation
calling it "not transient by default", because it is the catch-all for
unrecognized libpq errors and classing the unknown as transient errs toward
letting retries happen.

<Callout type="warn">
  **Behaviour change since `0.5.0.0`.** A
  `StatementSessionError` carrying a *server* error is now classified by
  SQLSTATE:

  ```haskell
  isTransientSqlState :: Text -> Bool
  isTransientSqlState code =
    code `elem` ["40001", "40P01", "55P03", "57P01", "57P02", "57P03"]
      || "53" `T.isPrefixOf` code
  ```

  That is serialization failure (`40001`), deadlock (`40P01`), lock timeout
  (`55P03`), admin shutdown, crash shutdown, and cannot-connect-now
  (`57P01`/`57P02`/`57P03`), plus all of class `53` (insufficient resources).

  On `0.4.0.1` every statement error maps to permanent unconditionally — so a
  retry loop gated on `isTransient` fails fast on exactly the errors retries
  exist for. Every *other* statement error, including decode and row-count
  mismatches, remains permanent on both versions.
</Callout>

## Traced interpreter

```haskell
data TracingConfig = TracingConfig
  { tracer :: !OTel.Tracer
  , recordExceptions :: !Bool
  , includeMessageBodies :: !Bool
  }

defaultTracingConfig :: OTel.Tracer -> TracingConfig

runPgmqTraced ::
  (IOE :> es, Error PgmqRuntimeError :> es) =>
  Pool ->
  OTel.Tracer ->
  Eff (Pgmq : es) a ->
  Eff es a

runPgmqTracedWith ::
  (IOE :> es, Error PgmqRuntimeError :> es) =>
  Pool ->
  TracingConfig ->
  Eff (Pgmq : es) a ->
  Eff es a
```

`runPgmqTraced` wraps every operation in an OpenTelemetry span. Send and topic
send operations are producer spans. Read, polling read, FIFO read, and `pop`
operations are consumer spans. Lifecycle and observability calls are internal
spans.

Span names use the OpenTelemetry v1.24-style form for compatibility:
`publish <destination>` for sends, `receive <destination>` for reads, and
`pgmq.<operation> <destination>` for lifecycle work. Operations without a queue
destination use only the operation name, such as `pgmq.list_queues`.

The traced interpreter emits old semantic-convention attributes by default and
uses `OTEL_SEMCONV_STABILITY_OPT_IN` to opt into stable or duplicate
messaging/database attributes:

```text
OTEL_SEMCONV_STABILITY_OPT_IN=messaging,database
OTEL_SEMCONV_STABILITY_OPT_IN=messaging/dup,database/dup
```

## Trace context helpers

```haskell
type TraceHeaders = RequestHeaders

injectTraceContext :: TracerProvider -> Context -> m TraceHeaders
extractTraceContext :: TracerProvider -> TraceHeaders -> Context -> m Context
traceHeadersToJson :: TraceHeaders -> Value
jsonToTraceHeaders :: Value -> TraceHeaders
mergeTraceHeaders :: TraceHeaders -> Maybe Value -> Value
```

Propagation uses the tracer provider's configured propagator. With the W3C
propagator this writes `traceparent` and `tracestate`; with B3 or Datadog it
writes that propagator's fields. `mergeTraceHeaders` is additive: existing user
headers win when a key already exists.

## Higher-level traced operations

```haskell
sendMessageTraced ::
  (Pgmq :> es, IOE :> es) =>
  TracerProvider ->
  QueueName ->
  MessageBody ->
  Maybe Value ->
  Eff es MessageId

type MessageWithContext = (Message, Context)

readMessageWithContext ::
  (Pgmq :> es, IOE :> es) =>
  TracerProvider ->
  ReadMessage ->
  Eff es (Vector MessageWithContext)
```

`sendMessageTraced` injects the current thread-local trace context into pgmq
headers and sends with `sendMessageWithHeaders`. `readMessageWithContext`
extracts a parent context from each returned message so the consumer can start
its own application-level process span.

## Unreleased inspection operations

<Callout type="info">
  These operations landed after published 0.6.1.1. They are available at reviewed source
  `mori://shinzui/pgmq-hs` commit `f4bdd914`, under both interpreters.
</Callout>

```haskell
peekMessages :: (Pgmq :> es) => PeekMessages -> Eff es (Vector Message)
peekArchivedMessages :: (Pgmq :> es) => PeekMessages -> Eff es (Vector ArchivedMessage)
lookupMessage :: (Pgmq :> es) => LookupMessage -> Eff es (Maybe Message)
lookupArchivedMessage :: (Pgmq :> es) => LookupMessage -> Eff es (Maybe ArchivedMessage)
queueMetricsUnvalidated :: (Pgmq :> es) => Text -> Eff es QueueMetrics
```

The effect gains five constructors: `PeekMessages`, `PeekArchivedMessages`, `LookupMessage`,
`LookupArchivedMessage`, and `QueueMetricsUnvalidated`. Custom interpreters that match every
constructor must handle them. The new argument records share names with effect constructors;
use qualified imports when matching the effect.
The built-in and traced interpreters retain the
[Hasql name, cursor, and non-leasing contract](/docs/pgmq/reference/hasql-api#unreleased-inspection-reads).
Missing queues surface as `PgmqSessionError`. Inspection spans are internal; the traced interpreter
does not add message bodies or headers to inspection spans, even when `includeMessageBodies` is enabled.

## Unreleased disconnect classification

<Callout type="info">
  This classifier change and helper landed after published 0.6.1.1. The published classifier
  still treats the lost-reply forms below as permanent and has no `isAmbiguousReply` export.
</Callout>

```haskell
isAmbiguousReply :: PgmqRuntimeError -> Bool
```

The reviewed source treats a server error with empty SQLSTATE in a statement or script as a lost
reply. It also recognizes exactly `UnexpectedRowCountStatementError 1 1 1`, the driver's extra-result
shape. Both are transient and ambiguous. Other row-count and decoding failures remain permanent.
Script server errors now use the same SQLSTATE rules as statement server errors.
`DriverSessionError` remains permanent.

`isAmbiguousReply err` implies `isTransient err`. A transient classification says that retry may
restore service; it does not establish that the operation had no effect. A send with a lost reply
may already have committed. Check durable application keys or use a duplicate-tolerant operation
before sending again. A later pool-connection error must not erase the earlier ambiguity.
The dead connection can cause one additional transient failure while the pool evicts it.

Read [Handle transient errors](/docs/pgmq/cookbook/handle-transient-errors) for retry decisions.
