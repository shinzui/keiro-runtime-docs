title: "Core types"
description: "The validated queue, message, routing, topic, and notification types from Pgmq.Types."
---

`pgmq-core` exposes one public module: `Pgmq.Types`. Other pgmq-hs packages reuse
these values, so import them directly when you need validated names or message
records without depending on a database client.

## Message values

```haskell
newtype MessageBody = MessageBody { unMessageBody :: Value }
newtype MessageHeaders = MessageHeaders { unMessageHeaders :: Value }
newtype MessageId = MessageId { unMessageId :: Int64 }
```

`MessageBody` wraps the JSON payload stored in pgmq's `msg` column.
`MessageHeaders` wraps arbitrary JSON metadata stored in the `headers` column.
Headers are where FIFO group keys and trace-propagation fields live. `MessageId`
is a pgmq row id represented as `Int64`.

<Callout type="info">
  Since `0.5.0.0`, a message whose body is SQL `NULL`
  decodes as `MessageBody Aeson.Null`, deliberately indistinguishable from an
  explicitly-sent JSON `null` body. The `message` column is nullable and
  `pgmq.send('q', NULL::jsonb)` is legal SQL for any non-Haskell producer. On
  `0.4.0.1` one such row makes every batch containing it fail at decode — after
  the read statement has already bumped `vt` and `read_ct` for the whole batch —
  and the row can be neither seen nor archived through this client.
</Callout>

```haskell
data Message = Message
  { messageId :: !MessageId
  , visibilityTime :: !UTCTime
  , enqueuedAt :: !UTCTime
  , lastReadAt :: !(Maybe UTCTime)
  , readCount :: !Int64
  , body :: !MessageBody
  , headers :: !(Maybe Value)
  }
```

`visibilityTime` is when the message can next be read. `readCount` is pgmq's
delivery counter. It increments when a message is leased, so retry and
dead-letter decisions should use it as an attempt signal rather than as proof
that the handler actually ran.

## Queue values

```haskell
data Queue = Queue
  { name :: !QueueName
  , createdAt :: !UTCTime
  , isPartitioned :: !Bool
  , isUnlogged :: !Bool
  }

newtype QueueName = QueueName Text
parseQueueName :: Text -> Either PgmqError QueueName
queueNameToText :: QueueName -> Text
```

`parseQueueName` rejects the empty string, and accepts only **lowercase** ASCII
letters, digits, and `_`. It limits the name so derived PostgreSQL identifiers
remain within PostgreSQL's 63-byte identifier limit; the effective queue-name
limit in this source is 47 characters because pgmq creates an
`archived_at_idx_`-prefixed identifier.

<Callout type="warn">
  **Lowercase-only is a correctness requirement, not a style rule.** pgmq's SQL
  lowercases physical table names while `pgmq.meta` stores the caller's original
  casing, and the notification trigger looks up the lowercased name. So
  `MyQueue` and `myqueue` were two logical queues silently interleaving in one
  physical table — dropping either destroyed the other's messages, and a
  mixed-case notification throttle was never matched by the trigger.

  A deployment whose `pgmq.meta` still holds mixed-case rows must be remediated
  before upgrading; see
  [Remediate mixed-case queue names](/docs/pgmq/how-to/remediate-mixed-case-queue-names).
</Callout>

<Callout type="info">
  Before `0.5.0.0`, `parseQueueName` accepted uppercase and let the empty string
  pass every check, and `FromJSON QueueName` was newtype-derived — accepting any
  string of any length, so configuration-loaded names bypassed validation. It is now a
  hand-written instance that validates via `parseQueueName`. `listQueues` also
  re-validates names read back from the database, which is what makes the
  remediation above a prerequisite rather than a cleanup.
</Callout>

Do not construct `QueueName` with unchecked text outside this package. Use
`parseQueueName` at configuration boundaries and store the validated value.

### Reading queues this client would reject

`UnvalidatedQueue` and `listQueuesUnvalidated` shipped in 0.5.0.0.

```haskell
data UnvalidatedQueue = UnvalidatedQueue
  { unvalidatedName :: !Text
  , unvalidatedCreatedAt :: !UTCTime
  , unvalidatedIsPartitioned :: !Bool
  , unvalidatedIsUnlogged :: !Bool
  }
```

A row of `pgmq.list_queues()` with the queue name left unvalidated. Queues are
created by every client that shares the database, and the server accepts names
`parseQueueName` rejects — its only check is length. This shape exists so state
inspection, notably pgmq-config's reconciler, can observe such foreign queues
without failing to decode them. `unvalidatedName` may therefore hold any
server-accepted name; do not feed it into APIs expecting a validated `QueueName`
without going through `parseQueueName`.

## Topic routing values

```haskell
newtype RoutingKey = RoutingKey Text
parseRoutingKey :: Text -> Either PgmqError RoutingKey
routingKeyToText :: RoutingKey -> Text

newtype TopicPattern = TopicPattern Text
parseTopicPattern :: Text -> Either PgmqError TopicPattern
topicPatternToText :: TopicPattern -> Text
```

Routing keys are dot-separated text up to 255 characters. `parseRoutingKey`
allows ASCII alphanumeric characters, `.`, `-`, and `_`; it rejects empty values
and wildcards. Topic patterns are also capped at 255 characters and may contain
the pgmq topic wildcards `*` and `#`.

```haskell
data TopicBinding = TopicBinding
  { bindingPattern :: !TopicPattern
  , bindingQueueName :: !Text
  , bindingBoundAt :: !UTCTime
  , bindingCompiledRegex :: !Text
  }

data RoutingMatch = RoutingMatch
  { matchPattern :: !TopicPattern
  , matchQueueName :: !Text
  , matchCompiledRegex :: !Text
  }

data TopicSendResult = TopicSendResult
  { sentToQueue :: !Text
  , sentMessageId :: !MessageId
  }
```

`TopicBinding` is returned by binding-list queries. `RoutingMatch` is returned
by dry-run routing tests. `TopicSendResult` is returned by batch topic sends and
identifies the queue/message pairs that received each routed message.

## Notification values

```haskell
data NotifyInsertThrottle = NotifyInsertThrottle
  { throttleQueueName :: !Text
  , throttleIntervalMs :: !Int32
  , throttleLastNotifiedAt :: !UTCTime
  }
```

`NotifyInsertThrottle` reports the throttle state for `LISTEN/NOTIFY` insert
notifications.

```haskell
notifyChannelName :: QueueName -> Text
notifyChannelName q = "pgmq.q_" <> T.toLower (queueNameToText q) <> ".INSERT"
```

`notifyChannelName` is the contract for the channel a queue's insert
notifications arrive on. Do not assemble the name by hand.

<Callout type="warn">
  **Correction.** These docs previously stated that notifications arrive on
  `pgmq_<queue_name>`. That was wrong, and it was wrong for `0.4.0.1` as well —
  the shipped trigger has always fired
  `PG_NOTIFY('pgmq.' || TG_TABLE_NAME || '.' || TG_OP, NULL)`, which yields
  `pgmq.q_<lowercased queue name>.INSERT`. Anyone who followed the old text
  listened on a channel that never receives anything. The `notifyChannelName`
  helper shipped in `0.5.0.0`; the channel name it returns is correct for
  `0.4.0.1` too.
</Callout>

## Parse errors

```haskell
data PgmqError
  = InvalidQueueName Text
  | InvalidRoutingKey Text
  | InvalidTopicPattern Text
```

These errors are local validation failures from `Pgmq.Types`, not database
runtime failures. Effectful database failures are represented separately by
`PgmqRuntimeError`.
