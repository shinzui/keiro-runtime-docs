Use ASD-STE100 Issue 9 as the writing reference for this documentation.
Use the project [technical terms](/docs/getting-started/technical-terms) for software concepts.

Keiro's terminology bundle supplies the project definitions. It is not the official STE dictionary.
The current editorial checks do not establish complete ASD-STE100 compliance.
Review general words, meanings, and parts of speech against the official standard before claiming compliance.
The [ASD website](https://www.asd-ste100.org/STE_downloads.html) provides the official copy by request.

## Release scope

Document the current supported behavior. Language 6 is the only supported Keiro DSL language.
Every complete `.keiro` example must declare `language keiro-dsl 6` before `context`.
Do not add tutorials for obsolete Keiro versions or the retired example application.

Use Mori to locate dependency source before describing an API.
Use canonical `mori://` references for artifacts in other repositories.
Record source-review evidence under `docs/`. Keep historical plans and review records outside the published content tree.

## Writing rules

Write instructions as commands. Use the active voice.
Give one action per step. State required conditions before the action.
Name the component that performs each action.

Keep procedural sentences within 20 words. Keep descriptive sentences within 25 words.
These limits are editorial checks, not permission to omit necessary conditions.
Split complex instructions into separate steps.
Keep descriptive paragraphs within six sentences and one subject.

Use the same term for the same concept. Define a technical term at its first use.
Use a noun for a named component and a verb for an action.
Write complete noun phrases with articles where needed.
Keep noun groups short. Use a preposition when a group becomes difficult to understand.

Do not use contractions, idioms, metaphors, or conversational comments.
Do not use an ambiguous pronoun when two components could be its subject.
Use simple verb forms. Avoid progressive verb forms.
Retain established technical nouns such as `event sourcing` and `consumer binding`.
Check each general word's approved meaning and part of speech against the official dictionary.

Keep API names, filenames, commands, wire values, and code unchanged during language edits.
A technical term does not permit unrelated uses of the same word.

## Page types

| Type | Purpose | Location |
| --- | --- | --- |
| Tutorial | Teach a complete working task. | `<product>/tutorials/` |
| How-To Guide | Give the steps for one task. | `<product>/how-to/` |
| Reference | Describe APIs, values, constraints, and errors. | `<product>/reference/` |
| Explanation | Explain a mechanism or design decision. | `<product>/explanation/` |
| Cookbook | Give a short complete recipe. | `<product>/cookbook/` |
| Code Walkthrough | Explain verified source in reading order. | `<product>/walkthrough/` |
| FAQ | Answer common questions. | `<product>/faq.mdx` |
| Integration | Explain contracts between products. | `integrations/` |

Use imperative steps in tutorials, how-to guides, and recipes.
Use present-tense descriptions in references, explanations, and walkthroughs.
Define mathematical notation before use.

## Names and files

Use lowercase product names: keiro, kiroku, keiki, shibuya, pgmq-hs, and pg-migrate.
Preserve the exact case of Haskell modules, APIs, and protocol names.
Use lowercase filenames with hyphens and the `.mdx` extension.
Use `index.mdx` for a section entry page.
Prefix walkthrough filenames with two digits to indicate reading order.

## Code and components

Use a language tag on every code fence.
Copy signatures from verified source. Include imports and prerequisites needed to use an example.
Label incomplete excerpts. Do not present an excerpt as a complete runnable program.

Use `mermaid` for diagrams. Label components and relationships with the documented terms.
The site provides `Callout`, `Steps`, `Step`, `Tabs`, `Tab`, `Cards`, `Card`, `Accordions`, `Accordion`, and `TypeTable`.
Use these components without per-page imports.
State a warning's condition and required action before the affected procedure.

## Add a page

1. Copy the appropriate template from `content/docs/_templates/`.
2. Save the file in its product and page-type directory.
3. Set the frontmatter `title` and `description`.
4. Write and verify the source-backed content.
5. Add the filename stem to that directory's `meta.json` `pages` array.
6. If you create a section, add its name to the parent metadata.
7. Run `pnpm run lint:docs` and review the prose report.
8. Run `pnpm check`.
9. Inspect the page, navigation, code, and diagrams in the browser.

Templates remain outside published navigation.

## Editorial checks

Refresh the Keiro terminology bundle before changing a definition in this site.
Locate it with `mori path mori://shinzui/keiro/okf/terminology`.
Validate it against the owning project's terminology profile and update its change log.
Run `pnpm run sync:terminology` to refresh the local snapshot and glossary.
Run `pnpm run lint:terminology` to check that the glossary matches its snapshot.
CI does not require an external source checkout.

`pnpm run lint:docs` rejects unsupported DSL declarations and common prose problems.
`pnpm run review:prose` reports sentence lengths and paragraph sizes across all published pages and templates.
The report includes frontmatter descriptions and visible component descriptions.
It excludes code and literal technical identifiers from English substitutions.

Sentence counts are estimates. Review findings in context.
The checks do not verify every dictionary meaning, part of speech, noun group, or grammatical construction.
Do not describe a passing check as certified STE compliance.
