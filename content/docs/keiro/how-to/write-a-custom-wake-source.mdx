title: "Write a custom wake source"
description: "Build a third-party wake source that resolves a suspended durable workflow without stranding it — the four obligations exact discovery makes mandatory, and the rotation race to handle."
---

You have an external system Keiro's built-in primitives do not model — a webhook fleet, a hardware
signal, a partner callback with its own durable queue — and you want a suspended workflow to continue
when it fires. That means writing a **wake source**.

<Callout type="warn">
  Since Keiro 0.12.0.0 this is a **correctness** obligation, not a performance detail.
  [Discovery is exact](/docs/keiro/reference/durable-workflows#discovery-is-exact): a `suspended`
  instance with no due wake hint is invisible to the resume worker. A wake source that transitions its
  own durable row without leaving the owning instance discoverable **strands that workflow
  permanently.** The old broad poll hid this class of bug by re-examining everything.
</Callout>

<Callout type="info">
  Assumes you have written a durable workflow and run the resume worker. If not, start with
  [Write a durable workflow](/docs/keiro/how-to/write-a-durable-workflow).
</Callout>

## Goal

A wake source that delivers a result to a workflow parked on `awaitStep`, survives a crash on either
side, and never leaves a workflow parked forever.

## The four obligations

Every wake source owes all four. The built-in sources — sleep, awakeables, child workflows — satisfy
them, and reading them as a checklist is the fastest way to review a new one.

1. **A durable row keyed by the logical workflow.** The wake must survive a restart of both your
   process and Keiro's. In-memory state is not a wake source.
2. **Delivery under the awaited step name.** The workflow suspends on a specific step name; you must
   append under exactly that name, or the run will not see its result on replay.
3. **An arm that re-checks the row and re-delivers.** Delivery is at-least-once. The arm runs on
   every replay, sees the row already resolved, and re-delivers idempotently.
4. **An instance-row write on every lifecycle transition.** Any transition that does *not* append —
   a cancellation, an abandonment, an expiry — must write the instance row itself.

## Steps

1. **Deliver through `appendJournalEntry`.** This is the whole shortcut for obligation 4: the append
   path already upserts the instance row to `running` in the same transaction as the journal append
   and the step-index write.

   ```haskell
   deliverCallback :: (IOE :> es, Store :> es) => WorkflowName -> WorkflowId -> StepName -> Value -> Eff es ()
   deliverCallback name wid (StepName step) payload = do
     now <- liftIO getCurrentTime
     appendJournalEntry name wid StepRecorded { stepName = step, result = payload, recordedAt = now }
   ```

   If you deliver this way and never abandon a wait, you are already compliant.

2. **Handle a terminal refusal.** The append transaction declines an ordinary `StepRecorded` into a
   generation that already carries a `__workflow_cancelled__` or `__workflow_failed__` marker.

   ```haskell
   outcome <- prepareJournalAppend name wid gen event >>= runTransaction
   case outcome of
     JournalRefusedTerminal marker -> settleOwnRowAndDeliverNothing marker
     JournalAppended _             -> pure ()
     JournalAlreadyPresent _       -> pure ()      -- at-least-once; already delivered
     JournalAppendConflict _       -> retryLater
   ```

   A refusal is **not an error**. It means the workflow went terminal while you were in flight.
   Settle your own durable row and deliver nothing.

3. **Write the instance row on every non-appending transition.** If your source can abandon a wait —
   a cancelled callback, an expired token — flip the owning instance row to `running` in the **same
   transaction** as your own row's transition, so the workflow is discovered and can observe the
   abandonment.

   This is exactly what `cancelAwakeable` does; its schema-level
   `cancelAwakeableTx` returns `Maybe (Text, Text)` — the owner's name and id — precisely so the
   caller can perform that write atomically.

4. **Never write `wake_after`.** It is a
   [sleep-only scheduling hint](/docs/keiro/reference/durable-workflows#the-wake_after-hint) owned by
   the first sleep arm. No other source may write it, and no source may rely on it for visibility.

## The rotation race

`continueAsNew` rotates the workflow onto a fresh generation, and the wake-source helpers resolve the
*current* generation internally. So a delivery that races a rotation can land on the new generation,
where the awaited step does not exist.

`appendJournalEntryReturningId` is the place this matters: it returns the id it appended, which is
what lets you record precisely what you delivered and to which generation.

<Callout type="warn">
  **Rotation abandons any promise id already handed out.** If your source issued an opaque id to an
  external party, the next generation re-runs the allocation step and issues a *fresh* one. Re-notify
  the holder from that step; a callback against the abandoned id resolves nothing.
</Callout>

## If you supply your own worker loop

A caller that runs Keiro's single-pass units inside its own loop inherits the
[worker-loop obligations](/docs/keiro/explanation/scaling-the-workers#worker-loops-isolate-failures):
isolate per pass, isolate per item, and report finished work rather than attempted work.
`resumeWorkflowsOnce`, `gcWorkflowsOnce`, `runTimerWorkerWith`, and `drainDueTimersWith` are the
testable units.

## Verify it worked

1. Suspend a workflow on your source, then confirm it is **invisible**:

   ```sql
   SELECT status, wake_after FROM keiro.keiro_workflows
   WHERE workflow_name = 'myWorkflow' AND workflow_id = 'inst-1';
   -- expect: suspended, NULL
   ```

   A resume pass should now report it under neither `discovered` nor `resumed`.

2. Fire your source, then confirm the same row flipped to `running` **in the delivering
   transaction** — not on a later pass.

3. Kill the process between your row's transition and the append, restart, and confirm the arm
   re-delivers and the workflow completes.

4. Cancel the workflow while a delivery is in flight and confirm your source observes
   `JournalRefusedTerminal` and settles without appending.
