You want each test to run against a **real**, **isolated**, **migrated** PostgreSQL database — but
starting a server and running migrations per test is far too slow. `Keiro.Test.Postgres` solves this
with a suite-level template database: one server, one migration pass, then a fast clone per example.

<Callout type="info">
  Assumes an `hspec` test suite and the `keiro-test-support` package as a test dependency. The
  fixture uses `ephemeral-pg`, which starts a throwaway PostgreSQL server for the suite.
</Callout>

## Goal

Run every `hspec` example against its own fresh, migrated `KirokuStore` without paying server-startup
and migration cost per test.

## Steps

1. **Wrap the whole suite in `withMigratedSuite`.** It starts one cached PostgreSQL server, creates a
   `keiro_template` database, and applies the native Kiroku + Keiro `pg-migrate` plan to it **once**:

   ```haskell
   import Keiro.Test.Postgres (withMigratedSuite, withFreshStore)
   import Test.Hspec

   main :: IO ()
   main =
     withMigratedSuite \fixture ->
       hspec $
         describe "orders" $ around (withFreshStore fixture) $ do
           it "appends an order-placed event" \store -> do
             -- store :: Kiroku.Store.KirokuStore, backed by a fresh isolated DB
             pure ()
   ```

2. **Use `withMigratedSuiteWith` when every clone needs extra components.** Resolve each library or
   application `MigrationComponent` and pass it in plan order. For example, add PGMQ to every clone:

   ```haskell
   import Pgmq.Migration qualified as Pgmq

   main =
     case Pgmq.pgmqMigrations of
       Left err -> fail (show err)
       Right pgmq ->
         withMigratedSuiteWith [pgmq] \fixture ->
           hspec $
             describe "orders" $ around (withFreshStore fixture) $ do
               it "uses the PGMQ schema" \store -> pure ()
   ```

   The fixture appends extras after Kiroku and Keiro in one plan. They must not be run as a second,
   partial plan: all components share the ledger, and strict verification rejects a plan that omits
   an already-recorded component as `UnknownStoredMigration`.

3. **Use `withFreshStore fixture` as the `around` action.** For each example it clones a fresh
   database with `CREATE DATABASE … TEMPLATE keiro_template`, opens a `KirokuStore` against it, runs
   the example, then drops the clone with `DROP DATABASE … WITH (FORCE)`. The expensive work
   (startup + migrations) already happened once in step 1; the clone is cheap.

4. **(Two databases) Use `withFreshStores2` for cross-context tests.** When a test needs two isolated
   databases — for example to exercise an outbox-to-inbox hop between two services — `withFreshStores2`
   provides a pair of independent stores cloned from the same template:

   ```haskell
   around (withFreshStores2 fixture) $ do
     it "delivers across two stores" \(storeA, storeB) -> pure ()
   ```

## Verify it worked

Run the suite (`cabal test`). Each example sees an empty, migrated database: the keiro tables exist
(migrations ran against the template) but carry no rows from other tests (each example got a fresh
clone). Writing a row in one example and asserting it is absent in the next confirms isolation.

The fixture uses `defaultRunOptions` and fails suite setup when component construction, plan
validation, or migration execution fails. Keep a separate CI `check --manifest` gate for authored
manifest changes and a strict `verify` gate for deployed databases.

## Fixture dependency set

Use `keiro-test-support 0.19.0.0` with Kiroku store `>=0.9.0.1 && <0.10`,
Kiroku migrations `^>=0.6.0.0`, and pg-migrate `^>=1.2.0.0`.
The fixture requires `ephemeral-pg >=0.3.1 && <0.4`.
`pg-migrate-test-support 1.2` accepts this ephemeral-pg line, so the former
`pg-migrate-test-support:ephemeral-pg` bound override is no longer needed.

Keiro suites and migration suites share `/tmp/ephpg-keiro-<uid>` so startup can reclaim abandoned
clusters across Nix and CI sessions. The root is selected internally; the public fixture API is unchanged.

## Upstream runtime verification

The source repository `mori://shinzui/keiro` also runs `keiro-retention` in `just verify`.
It measures live heap after major garbage collection across isolated store, adapter, worker,
command, hydration, and tail-read workloads. Every leg checks its durable result as well as the
retained heap trend. These finite regression gates do not establish that every workload is leak-free.
Sampled snapshot verification has a separate process-wide capacity limit.

The same verification command checks `keiro-reexports`: generated imports from `keiro-core`
must also be available through `keiro`. This catches omissions that an in-repository conformance
suite with a direct core dependency cannot detect. Consumers should still compile and test their
own generated service against the selected published package set.
