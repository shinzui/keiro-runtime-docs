The types and functions on this page live in `Keiro.Projection`. A projection folds events into an
application-owned read-model table; see
[Projections, read models, and snapshots](/docs/keiro/explanation/projections-read-models-and-snapshots)
for the conceptual distinction.

<Callout type="warn">
  Projection inputs are events, never aggregate state. `InlineProjection.apply` receives `(co,
  RecordedEvent)` and `AsyncProjection.applyRecorded` receives `RecordedEvent`. Neither API receives
  Keiki `RegFile`, a Keiro aggregate snapshot, or a `deriveView` result. A rebuild must reproduce the
  table by replaying these event inputs.
</Callout>

## `InlineProjection`

<TypeTable
  type={{
    name: { type: "Text", description: "Logical name of the projection" },
    apply: { type: "co -> RecordedEvent -> Tx.Transaction ()", description: "Fold one decoded and recorded event into the application table" },
  }}
/>

`runCommandWithProjections` delegates to `runCommandWithSqlEvents`; the append and every inline
`apply` share one transaction. A projection failure aborts the append, so events and read-model rows
commit together or not at all. Like the other SQL command runners, this function requires
`KirokuStoreResource` so Kiroku enrichment runs before the callback sees recorded events.

```haskell
runCommandWithProjections ::
  ( HasCallStack, IOE :> es, Store :> es, Error StoreError :> es
  , KirokuStoreResource :> es, BoolAlg phi (RegFile rs, ci), Eq co ) =>
  RunCommandOptions ->
  ValidatedEventStream phi rs s ci co ->
  Stream (EventStream phi rs s ci co) ->
  ci ->
  [InlineProjection co] ->
  Eff es (Either CommandError (CommandResult (EventStream phi rs s ci co)))
```

Keiro supplies the per-event transaction, deduplication, and registry fence. It does not supply the
subscription polling loop or checkpoint acknowledgement policy.

## Live application outcomes

```haskell
data AsyncApplyOutcome
  = AsyncApplied
  | AsyncDuplicate
  | AsyncFenced

applyAsyncProjection ::
  AsyncProjection -> RecordedEvent -> Tx.Transaction AsyncApplyOutcome
```

`applyAsyncProjection` reads `readModelName` from `keiro.keiro_read_models` with `FOR SHARE` in the
same transaction as the dedup insert and application write.

| Outcome | Database effect | Worker disposition |
| --- | --- | --- |
| `AsyncApplied` | Dedup key and read-model update commit together. | Acknowledge/checkpoint when the enclosing delivery transaction succeeds. |
| `AsyncDuplicate` | Existing retained dedup key suppresses `applyRecorded`. | Treat as idempotent success and acknowledge/checkpoint. |
| `AsyncFenced` | Registry row is missing or not `Live`; no dedup or model write occurs. | Do **not** acknowledge or checkpoint past the event. Fail/park it and retry after promotion. |

That last rule is essential: checkpointing `AsyncFenced` would permanently skip an event while a
rebuild owns the model.

## Rebuild-only application

```haskell
applyAsyncProjectionUnfenced ::
  AsyncProjection -> RecordedEvent -> Tx.Transaction AsyncApplyOutcome
```

This bypasses the registry status check so the designated rebuilder can write while the model is
`Rebuilding`. It still inserts the projection/event dedup key, so its outcomes are `AsyncApplied` or
`AsyncDuplicate`. Live workers must use `applyAsyncProjection`; never use the unfenced function to
avoid handling `AsyncFenced`.

## Dedup retention

```haskell
pruneAsyncProjectionDedupBefore :: UTCTime -> Eff es Int64
```

The dedup key and `applyRecorded` run in the same transaction. Prune only before the oldest event the
subscription system can redeliver; pruning intentionally reopens older events for application. It
is not a rebuild reset. `startRebuild` clears only the named projections' keys atomically with the
writer fence, table truncation, and checkpoint reset.

## Projection lag

```haskell
recordProjectionGlobalPositionDistance ::
  Maybe KeiroMetrics -> AsyncProjection -> Eff es ()

recordProjectionLag ::                    -- deprecated compatibility alias
  Maybe KeiroMetrics -> AsyncProjection -> Eff es ()
```

Call this from the application-owned drain loop, normally after applying a batch. It records the
captured store position minus the projection's slowest durable member checkpoint; `Nothing` makes it
a no-op.

<Callout type="warn">
  **Prefer `recordProjectionGlobalPositionDistance` since Keiro 0.12.0.0.** The value is a distance
  between two **positions**, not a count of events — a global cursor can be sparse for a filtered,
  category, hard-deleted, or sharded history. `recordProjectionLag` remains as a one-series
  compatibility alias recording the same value to the deprecated `keiro.projection.lag` gauge, whose
  unit changed from `{event}` to `{position}`. See
  [the deprecation note](/docs/keiro/reference/telemetry#keiroprojectionlag-is-deprecated).
</Callout>

## Catalog-aware application

When a service declares a
[projection catalog](/docs/keiro/reference/projection-catalog), use the catalog-aware entry points so
inline and async application respect the rebuild-group writer fence:

```haskell
runCommandWithCatalogProjections :: … -> Eff es ProjectionCommandOutcome
applyAsyncProjectionFromCatalog  :: … -> Eff es CatalogAsyncApplyOutcome
```

Both take the same sorted group locks and return typed **fenced** outcomes without committing the
append, the dedup write, or any target write. The uncatalogued functions above remain supported for
services that have not adopted a catalog.

Dedup maintenance gains per-projection forms, `countAsyncProjectionDedupForBefore` and
`pruneAsyncProjectionDedupForBefore`, which back
[`keiro-ops projection prune-dedup`](/docs/keiro/reference/keiro-ops-cli#projection--projection-state).

See [Make an async projection idempotent](/docs/keiro/how-to/make-an-async-projection-idempotent)
for a complete outcome handler and
[Rebuild a read model](/docs/keiro/how-to/rebuild-a-read-model) for fenced replay.

## Guarded catalog commands

Keiro 0.20 adds an opt-in transactional precondition. Keiro 0.21 retains the API:

```haskell
runDomainCommandWithCatalogProjectionsGuarded ::
  forall phi rs s ci co rejection noOp refusal es.
  (HasCallStack, IOE :> es, Store :> es, Error StoreError :> es, KirokuStoreResource :> es, BoolAlg phi (RegFile rs, ci), Eq co) =>
  RunCommandOptions ->
  DomainCommandHandler phi rs s ci co rejection noOp ->
  Stream (EventStream phi rs s ci co) ->
  ci ->
  ValidatedProjectionCatalog ->
  ProjectionSet co ->
  (CatalogPreconditionContext -> Tx.Transaction (Either refusal ())) ->
  Eff es (Either CommandError (GuardedCatalogOutcome (EventStream phi rs s ci co) co rejection noOp refusal))
```

```haskell
data GuardedCatalogOutcome target co rejection noOp refusal
  = CatalogCommandOutcome !(DomainProjectionCommandOutcome target co rejection noOp)
  | PreconditionRefused !refusal
  deriving stock (Generic, Eq, Show)

catalogPreconditionBindings :: CatalogPreconditionContext -> [ProjectionWriteBinding]
```

Catalog admission locks all required groups and resolves their serving bindings before invoking
the callback after tentative append. Returning `Left refusal` rolls back append and projection
writes and returns no accepted receipt; `Right ()` delivers inline handlers using those same
protected bindings. Fenced/missing/invalid catalog outcomes take precedence over consumer SQL.
Silent pure-domain decisions invoke neither callback nor catalog transaction. A captured context
does not retain locks or authorize another transaction.

The guard is trusted, bounded, retryable transaction-local application SQL. Use indexed reads and
return refusal through `Either`. Do not condemn/control transactions, change isolation, acquire
new stream/group locks, append recursively, or perform effects that survive rollback. The callback
sees its own tentative append; that does not identify a committed winner. All creation paths must
participate in the same Kiroku global append serialization and synchronous authority for an atomic
identity invariant. Async projections and unrelated external writers do not establish that guarantee.

`ProjectionSet` group selection includes async-only owners. Supply an inline-only subset of the
full catalog's definitions when a command must remain independent of async-view availability.
Every post-append guard statement extends the store-wide append lock. `RunCommandOptions` bounds
OCC retries, not Hasql's transaction retries. Implementation evidence does not establish a calibrated
throughput or latency guarantee. Rich query models remain asynchronous by default.

Follow [guard a catalog command](/docs/keiro/how-to/guard-a-catalog-command) for authority selection, callback restrictions, and concurrent verification.
