A **service workspace** validates, scaffolds, and diffs several complete `.keiro` files as **one
service contract**. A `.keiro-workspace` manifest names the service and lists its members; shared ids,
enums, rules, and [mapped structural types](/docs/keiro/reference/keiro-dsl-mapped-types) resolve once
across all of them, so an aggregate in one file may use a declaration owned by another or feed a read
model owned by a third.

A single `.keiro` file is unchanged and behaves as a **one-member workspace**.

<Callout type="warn">
  **Unreleased.** Workspaces are shipped and CLI-dispatched in the keiro source tree but sit in
  `keiro-dsl`'s `[Unreleased]` changelog section — they are **not** in the `0.4.0.1` release this
  documentation otherwise pins. Everything below is transcribed from committed source at the reviewed
  commit; treat it as a preview of the next release, not as an API you can depend on from Hackage.
</Callout>

## The manifest

```text
# The demo-project service workspace.
service demo-project
module Demo.Modules.Project
layout collocated
spec domain/project-artifact.keiro
spec domain/project.keiro
spec domain/shared.keiro
```

Line-oriented in the spirit of the member grammar: `#` starts a comment, blank lines are
insignificant, and clause keywords drive structure. The member `.keiro` grammar is untouched.

<TypeTable
  type={{
    service: { type: "required", description: "The stable workspace identity, e.g. demo-project. Keys the scaffold record, so it outlives member renames." },
    module: { type: "optional", description: "The workspace's module-root authority. A member's own module clause may not contradict it." },
    layout: { type: "optional", description: "The workspace's placement authority (e.g. collocated). Same rule as module." },
    spec: { type: "one or more", description: "A manifest-relative member path ending in .keiro. Normalized to forward slashes with no ./ segments." },
  }}
/>

**Membership is a set.** `spec` lines are accepted in any order and canonically sorted (codepoint order
on the normalized relative path); `keiro-dsl parse <manifest>` always emits that canonical order. Source
order therefore never changes the parsed manifest, the merged graph, or a single generated byte.

<Callout type="info">
  It is a **file**, not repeated CLI flags, for two reasons: `diff --since <rev>` must be able to
  reconstruct the member set *as it existed at an older git revision* from git alone, and the scaffold
  record needs one durable identity that survives member renames.

  Dispatch is on the **extension**, case-insensitively, and never on content — a corrupted manifest
  must produce a manifest parse error rather than a confusing `.keiro` one.
</Callout>

## Composition and its refusals

Composition produces one merged `Spec` holding every member's declarations and nodes in canonical
member order, with line numbers relocated into disjoint ranges. Because the result is an *ordinary*
`Spec`, the existing whole-spec validation, type-graph resolution, coverage, and binding analysis all
run over it unchanged — cross-file references resolve by name exactly as if the members had been one
file, with no risk of a node-specific rule diverging between the single-file and workspace paths.

Composition refuses, **before producing a graph**, when:

| Refusal | Code |
|---|---|
| a member file cannot be read | `WorkspaceMemberUnreadable` |
| a member file fails to parse | `WorkspaceMemberParseFailed` |
| members declare **different contexts** | `WorkspaceContextMismatch` |
| a member's `module`/`layout` clause contradicts the manifest authority | `WorkspaceAuthorityConflict` |
| a shared declaration is owned by two members | `WorkspaceDuplicateDeclaration` |
| a node name is owned by two members | `WorkspaceDuplicateNodeName` |
| two members claim generated module paths that collide **under case folding** | `WorkspacePathCollision` |

<Callout type="warn">
  **Identical duplicates never silently merge.** Two members declaring the same id with the same
  definition is still `WorkspaceDuplicateDeclaration` — ownership must be unambiguous, because the
  scaffold record attributes each emitted module to exactly one member.
</Callout>

Manifest *syntax* and structure errors deliberately carry **no diagnostic code**. Like a `.keiro` parse
error, they are refused before any graph exists to diagnose — the code registry describes findings
about a graph.

## Multi-file diagnostics

One diagnostic can cite several files. The primary location keeps the established single-file shape and
each further location follows as an indented `note:` line:

```text
domain/project.keiro:14: error[WorkspaceDuplicateDeclaration]: id ProjectId is declared by two members
  note: domain/shared.keiro:3: also declared here
```

## CLI behaviour

Every command accepts a manifest in place of a `.keiro` path:

| Command | On a manifest |
|---|---|
| `parse` | round-trips the manifest canonically (clauses in order, members codepoint-sorted) |
| `check` | composes the whole service and validates it as one contract |
| `scaffold` | plans and executes a **whole-workspace** scaffold with workspace-keyed history |
| `diff --since <rev>` | reconstructs the old member set from git and diffs whole-service |

`check`'s success options all work against the merged graph: `--emit` prints the canonical
whole-service view, `--explain-bindings` lists the service's binding obligations, and
`--coverage-report` / `--fail-on-opaque` report on the merged mapped-type graph with the manifest as
the report's subject. See [the CLI reference](/docs/keiro/reference/keiro-dsl-cli).

## Workspace-keyed scaffold history

A workspace record answers three questions a context-keyed
[scaffold record](/docs/keiro/reference/keiro-dsl-cli#scaffold-record-and-stale-paths) cannot: which
*service* produced this output tree, which member files it was composed from, and **which member
produced each emitted module**. That last one is what makes moving an aggregate between member files an
**ownership move** rather than a stale/new pair.

The record is keyed by service name in a distinct file-name slot —
`keiro-dsl-scaffold-record.workspace.<service>.txt` — and never by context:

```text
keiro-dsl workspace scaffold record v1
service: demo-project
manifest: service.keiro-workspace
context: demo-project
module-root: Demo.Modules.Project
layout: collocated
member domain/project.keiro
module {"kind":"generated","path":"Demo/Project/Generated/StructuralProjections.hs"}
module {"kind":"generated","path":"Demo/Project/Project/Generated/Domain.hs","owner":"domain/project.keiro"}
mapping {…}
binding {…}
adopted {"path":"…","evidence":"record","source":"keiro-dsl-scaffold-record.demo-project.txt"}
```

`module` rows are canonical single-line JSON. An **absent `owner`** means the module is context-level:
emitted once for the whole merged graph (the structural-projection facade, the replay-audit assembly, or
a binding skeleton shared by declarations from several members). Unknown row kinds and unknown JSON keys
are ignored so a later tool version can extend the schema; paths that are absolute or contain `..` are
rejected rather than joined to an output root.

<Callout type="info">
  **Legacy and workspace records coexist safely.** A context name lexes as letters, digits, `_` and `-`
  and can never contain a dot, so the workspace slot provably cannot collide with a legacy
  context-keyed name — even when a service is named after its context. An older `keiro-dsl` binary is
  structurally incapable of parsing, and therefore of clobbering, workspace history.
</Callout>

## Adopting pre-workspace output

The first whole-workspace scaffold into a directory that already holds per-context output must answer
*which of these files are mine?* — and guessing either way is harmful. Claiming everything would take
ownership of hand-written code and overwrite it next run; claiming nothing would dump the whole
existing tree on a human to reconcile.

So adoption claims only what is **attributable**, with the evidence recorded:

| Evidence | Meaning |
|---|---|
| `record` | the file is listed in a legacy per-context record for this workspace's effective context, **and** the workspace still produces it |
| `banner` | the file sits at a path this workspace produces as Generated and carries the `-- @generated` banner, but no surviving record lists it — the orphan case where two same-context specs scaffolded into one directory and the second overwrote the first's record |

Everything else is reported and left alone:

- **Hole paths are never claimed** — the create-once rule keeps governing them.
- Files the plan never mentions are listed as **unclaimed**.
- Files the legacy record lists that this workspace no longer produces are listed as **likely stale**,
  and are deliberately *not* merged into the workspace record: the record states what this workspace
  produces and adopted, not what an abandoned scaffold once produced.

**Nothing is deleted and nothing is renamed.** The legacy record gains exactly one appended
`superseded-by:` line, which its own v1 parser ignores, so an older binary keeps reading it unchanged.

## Whole-workspace diff

`diff --since <rev>` resolves the old member set from the manifest as it existed at that revision, so a
member added, removed, or renamed between revisions is understood rather than seen as a mass
add/delete. Beyond ordinary wire evolution it reports two workspace-specific advisories:

| Code | Trigger | Obligation |
|---|---|---|
| `OwnershipMoved` | a declaration or node moved from one member file to another | re-scaffold; generated module paths and their owners change even though the contract did not |
| `WorkspaceAuthorityChanged` | the manifest's `module` or `layout` authority changed | re-scaffold; every generated module path is affected |

Both are **advisory consumer-build obligations**, deliberately distinct from wire evolution: nothing
persisted changed, but hand-owned code that imports the generated modules will not compile until it is
re-scaffolded. A workspace `--report-out` adds a top-level `workspace` object and optional per-finding
`declaration` and `useSites` keys; single-file reports keep their original bytes.
