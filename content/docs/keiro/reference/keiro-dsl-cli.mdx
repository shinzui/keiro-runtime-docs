Run `keiro-dsl` from an installed environment. In the Keiro source tree, use
`cabal run keiro-dsl --` or put `keiro-dsl/bin` on `PATH`.

## Command summary

```text
keiro-dsl new <kind>
keiro-dsl parse <FILE>
keiro-dsl pretty <FILE>
keiro-dsl inspect <FILE> [--format=json]
keiro-dsl behavior-obligations <FILE> [--format=text|json]
keiro-dsl check <FILE> [--emit] [--explain-bindings] \
  [--coverage-report FILE [--fail-on-opaque]]
keiro-dsl scaffold <FILE> --out DIR \
  [--module-root PREFIX] [--collocate] [--force-generated-overwrite] [--goldens DIR] \
  [--codec-comparison MAPPED-NAME --comparison-out FILE]
keiro-dsl diff --since <git-ref> <FILE> \
  [--emit-goldens DIR] [--replay-impact-out FILE] \
  [--gate SURFACE]… [--explain] [--report-out FILE] \
  [--coverage-report FILE [--fail-on-opaque-increase]]
```

`FILE` is a path to a `.keiro` spec **or** a `.keiro-workspace` manifest, and can be `/dev/stdin`.
Dispatch is by extension: a path ending in `.keiro-workspace` takes the
[workspace](/docs/keiro/reference/keiro-dsl-workspaces) path, everything else takes the single-file
path described here.

## `new`

`new` prints a minimal, guaranteed-valid starter to stdout. The closed kind vocabulary is:

```text
aggregate process router contract intake emit publisher workqueue dispatch workflow operation
```

```bash
keiro-dsl new aggregate > service.keiro
keiro-dsl check service.keiro
```

`readmodel` is a top-level node but has no standalone starter. The `workqueue` starter includes the
read models needed by its dispatch example. Each starter is compiled by the upstream skeleton
conformance suite.

<Callout type="info">
  *(Keiro 0.9.0.0.)* Every skeleton now begins with a `language keiro-dsl 4` preamble, because
  language 4 is the sole `Stable` registry entry. The starter version is **derived** from that
  registry fact rather than hard-coded, so a future stable designation moves the skeletons with it.
  See [language versions](/docs/keiro/reference/keiro-dsl-language-versions).
</Callout>

## `parse`

`parse` parses and pretty-prints the canonical spec. It exits 0 on success and nonzero with a located
syntax error on failure.

```bash
keiro-dsl parse service.keiro
```

The parser rejects raw newlines in strings, duplicate singleton aggregate clauses (`wire`,
`projection`), duplicate transition `goto`, invalid identifiers, overflowed `Int` literals, and
missing grammar-mandatory policy arms before semantic validation runs.

## `pretty`

`pretty` parses a `.keiro` file and prints its **canonical source form**. Note that canonical
printing is deliberately **non-lossless** — comments and whitespace are not retained.

```bash
keiro-dsl pretty service.keiro
```

## `inspect`

*(Keiro 0.6.0.0.)* `inspect` reports **source-language provenance** as JSON, for a single `.keiro`
file or a whole workspace manifest.

```bash
keiro-dsl inspect service.keiro --format=json
keiro-dsl inspect service.keiro-workspace --format=json
```

It answers three separate questions per source: what the file **declared** (a version, or
`legacy-unversioned`), what version is therefore **effective**, and what that version's **support
lifecycle** is — `stable` for language 4, `compatibility-only` for 1 through 3.

<Callout type="info">
  The declared/effective split is not pedantry. A workspace can hold a legacy-unversioned member and
  an explicitly-version-1 member; both are effective version 1, but only one of them said so. `inspect`
  reports each member honestly rather than inventing one declaration for the merged graph. The same
  rows appear in scaffold and workspace records. See [language
  versions](/docs/keiro/reference/keiro-dsl-language-versions).
</Callout>

## `behavior-obligations`

*(Keiro 0.7.0.0.)* `behavior-obligations` inventories the **complete finite behaviour surface** of
every version-2 aggregate in a file or workspace — a static listing, with no compilation and no
consumer code involved.

```bash
keiro-dsl behavior-obligations service.keiro --format=text
keiro-dsl behavior-obligations service.keiro --format=json
```

Three obligation kinds are enumerated:

- every **live transition** from a live-reachable state;
- every **reachable rejection cell** — a (state, command) pair that is reachable and has no
  accepting transition; and
- every **replay-only transition**.

Each row carries a stable semantic key and its owning workspace member. Rows are **additive**: a
scaffold record retains the key and owner across runs, so an obligation can be tracked over time.

<Callout type="warn">
  This command reports what your specification **obliges**, never what a consumer has actually
  filled — the records deliberately make no fill-status claim. Proving obligations are met is the
  compiled conformance report's job; see [prove aggregate behaviour is
  complete](/docs/keiro/how-to/prove-aggregate-behavior-is-complete).
</Callout>

## `check`

`check` runs all single-spec validators. With no error-severity diagnostic it prints `OK` and exits
0. Warnings are printed and still exit 0. Any error exits nonzero.

```bash
keiro-dsl check service.keiro
keiro-dsl check service.keiro --emit
```

`--emit` prints the canonical accepted spec instead of `OK`, combining parse, validation, and
normalization.

The diagnostic form is:

```text
service.keiro:<line>: <error|warning>[Code]: <message>
```

Fix the `.keiro` source. Scaffold calls the same validator and cannot generate an invalid spec.

### `--explain-bindings`

On success, instead of `OK`, print a deterministic report of every **consumer-owned symbol** that
[structural mapped types](/docs/keiro/reference/keiro-dsl-mapped-types) require you to write by hand
— binding, fixture, and register-initial symbols, with their package, module, signature, and
use sites:

```bash
keiro-dsl check service.keiro --explain-bindings
```

This is the answer to "the scaffold left me holes; what exactly do I owe, and where does each one get
used?" It resolves the mapped type graph, so a spec that validates but whose graph does not resolve
exits nonzero with the graph errors.

### `--coverage-report FILE` and the opacity gates

Write **reporting-only** structural/opaque mapped-root coverage as JSON:

```bash
keiro-dsl check service.keiro --coverage-report coverage.json
```

Without a gate flag, coverage is purely informational — it never changes the exit code. Two opt-in
gates turn it into a policy check (each requires `--coverage-report`):

| Flag | Command | Fails when |
|---|---|---|
| `--fail-on-opaque` | `check` | a **private persisted root** still contains an opaque boundary |
| `--fail-on-opaque-increase` | `diff` | the change **adds** a named opaque boundary |

<Callout type="info">
  The default is deliberately reporting-first: opacity is a legitimate modelling choice, and which
  roots must be fully structural is an operator decision, not a validator's. Adopt `--fail-on-opaque`
  once a service has finished its structural adoption, and `--fail-on-opaque-increase` from the start
  to ratchet.
</Callout>

## `scaffold`

```bash
keiro-dsl scaffold service.keiro --out gen
```

The command has a plan-then-write boundary. Before any write it checks:

1. semantic validation;
2. exact and case-folded module-path collisions;
3. faithful type and policy lowering;
4. the symbolic-operator firewall; and
5. that every existing generated target contains `-- @generated`.

Any refusal exits 1 and writes nothing. `--force-generated-overwrite` bypasses only the fifth check;
use it to adopt a reviewed file as generated output, never as a general recovery switch.

Placement precedence is CLI flag, then spec clause, then default:

```bash
keiro-dsl scaffold service.keiro --out src --module-root Acme --collocate
```

On success, stderr lists every module and disposition (`overwritten`, `created`, or
`skipped: already present`), the firewall verdict, harness modules, and manifest path.

### `--goldens DIR`

Embeds versioned old-payload fixtures into the generated aggregate harnesses, which then exercise
each one through `decodeRaw`. The default root is `<spec-dir>/golden-payloads`, so a project that
adopts the convention needs no flag. Capture the fixtures with `diff --emit-goldens` at the moment of
a version bump — see below.

### `--codec-comparison MAPPED-NAME --comparison-out FILE`

The two flags are a pair; supplying one without the other is an error. Together they emit a
**non-production** historical-codec comparison module and runner for one structural mapped type:

```bash
keiro-dsl scaffold service.keiro --out gen \
  --codec-comparison ShippingAddress \
  --comparison-out gen/Generated/Ordering/Structural/Compare/ShippingAddress.hs
```

`--comparison-out` must be the **exact** generated module path under `--out`; a mismatch is refused
before anything is written, with the expected path in the message.

The generated runner classifies RFC 8785 canonical-JSON parity between the **declared** codec and a
**historical** one, reporting structured migration differences plus declared-versus-observed branch
coverage gaps. Use it to *prove* a migration rather than assert it.

<Callout type="warn">
  The comparison module and its runner are **evidence, never a wire authority**. Wire policy lives
  exclusively in the checked declaration and the generated codec. Do not import a comparison module
  from production code, and do not treat its output as a licence to skip a version bump.
</Callout>

### Replay-audit module

Every scaffold emits one context-wide `Generated.<Context>.ReplayAudit` exporting
`auditTargets :: [SomeAuditTarget]`: every aggregate in declaration order, each validating discovered
stream names against its generated category. Its header states the deployment contract — a
replay-neutral diff needs no audit, an affected diff needs `AuditTargeted`, a runtime cutover needs
`AuditFull`, and any non-zero exit blocks deployment. See
[Replay audit](/docs/keiro/reference/replay-audit).

### Manifest

`keiro-dsl-manifest.<context>.txt` contains paste-ready `other-modules:` and `build-depends:` blocks.
It is the authority for wiring one concrete scaffold into Cabal.

### Scaffold record and stale paths

`keiro-dsl-scaffold-record.<context>.txt` records the planned paths. A later run reports paths it no
longer emits under `stale:` and exits 0. Scaffold never deletes them:

- `generated` entries are deletion candidates after review;
- `hole` entries are hand-owned and require code inspection.

If the report says the previous spec path differs, two specs share one context and output directory.
Separate the outputs unless that ownership is deliberate.

## `diff`

`diff` loads the prior file with `git show`, parses both specs, and classifies the complete persisted
decode and identity registry:

```bash
keiro-dsl diff --since HEAD service.keiro
```

Each line is regular:

```text
ADDITIVE: <node> <facet> <subject>: <detail>
WARNING: <node> <facet> <subject>: <detail> [Code]
BREAKING: <node> <facet> <subject>: <detail> [Code]
```

| Tier | Exit effect | Meaning |
|---|---|---|
| `ADDITIVE` | 0 | A compatible surface was added |
| `WARNING` | 0 | Forward policy/behavior changed and requires review |
| `BREAKING` | nonzero | Persisted bytes, rows, cursors, jobs, or derived IDs can remain under the old contract |

### Compatibility vectors

A single tier per finding was too coarse: one change can be safe for stored history and unsafe for a
consumer's build, and which of those blocks *your* deploy depends on your rollout. So each finding
carries a **compatibility vector** — an independent verdict on six surfaces:

| Surface (`--gate` name) | The question it answers |
|---|---|
| `private-history-read` | can this binary still read its own stored history? |
| `old-binary-read-new-events` | can a **not-yet-upgraded** binary read events the new one writes? |
| `snapshot-hydration` | do existing snapshots still hydrate, or is a rebuild forced? |
| `public-consumer` | does a published contract change under consumers? |
| `persisted-identity` | does a durable identity (ID prefix, category, stable name, table, queue) move? |
| `consumer-build` | does hand-owned consumer code still compile? |

Each surface gets `compatible`, `advisory`, `breaking`, or `n/a`. When the vector is **not uniform**,
`diff` prints it as a second indented line, omitting `n/a` surfaces and appending any rollout
constraint:

```text
BREAKING: aggregate event OrderPlaced: payload changed without a version bump [EventPayloadChanged]
    vector: private-history-read=breaking snapshot-hydration=advisory consumer-build=breaking rollout=workers-first
```

The four rollout constraints are `stop-the-world`, `workers-first`, `drain-required`, and
`producer-last`. A finding with any rollout constraint is at least `WARNING`, even when no surface is
breaking — the bytes are fine but the *order* is not.

The printed tier is derived from the vector and the active gate: `BREAKING` when any **gated** surface
is breaking, `WARNING` when any surface is advisory-or-breaking or a rollout constraint is present,
`ADDITIVE` otherwise.

### `--gate SURFACE`

The default gate is **every surface except `old-binary-read-new-events`** — that one is excluded
because a rolling deploy where old binaries briefly see new events is normal, and gating it by default
would block ordinary additive work. `--gate` is repeatable and only ever *adds* to the default set:

```bash
# Also block on old binaries reading new events — for a deploy that cannot be ordered.
keiro-dsl diff --since origin/main --gate old-binary-read-new-events service.keiro
```

There is no flag to *remove* a surface from the gate. Accept a breaking verdict by changing the spec
or by making the deploy decision outside the tool, not by loosening the gate.

### `--explain`

Print, for every finding with an advisory or breaking surface, the containing paths, which direction
each affected surface fails in, and the remediation choices:

```text
explain [EventPayloadChanged]
  path: …
  direction: private-history-read is breaking; …
  remedy: …
```

Remedies are drawn from a closed vocabulary — version bump, upcaster, deployment order, contract
revision, replay-only edge, state-codec bump, recompile consumers, re-scaffold workspace, run
conformance, or an explicit do-not-deploy.

### `--report-out FILE`

Write the full machine-readable report, schema `keiro-dsl/diff-report/1`. It carries the active gate
and every finding with its vector. **Consumers must ignore unknown object keys**: vector keys and
`paths` entries are append-only, so later work can refine findings without invalidating a version-1
reader. A workspace input adds a top-level `workspace` object and optional per-finding `declaration`
and `useSites` keys; single-file reports keep their original bytes.

Examples of breaking identity include an ID prefix, process category, workflow stable name, router
stable name/key/target, read-model table/subscription, or queue identity. Event payload changes need
a version bump and contiguous `upcast from v(N-1) = HOLE`; a **vanished upcaster rung** is breaking
(`UpcasterChainGap`). A removed event remains decodable with `deprecated event` — but decodable is not
replayable, so `diff` distinguishes a hazardous deprecation from the replay-safe
deprecated-plus-`replay-only` cutover.

### Non-breaking advisories

These exit 0 but carry an operational obligation:

| Code | Trigger | Obligation |
|---|---|---|
| `AggGuardTightened` | a live guard changed with no replay-only twin | paste the printed twin, or audit and truncate |
| `AggFoldSurfaceChanged` | the spec-visible replay surface moved | expect one full replay per snapshot-bearing stream |
| `DeprecatedEventReplayHazard` | a deprecated event has no replay-only emitter | restore the inverting edge, or terminalize/truncate |
| `EventRetirementInProgress` | the safe retained shape is in place | keep the cleanup on the backlog |
| `RouterDecideSurfaceChanged` | router resolve/dispatch changed | drain the subscription redelivery window |
| `ProcessDecideSurfaceChanged` | process handle surface changed | drain the subscription redelivery window |
| `ProcessTimerPayloadChanged` | an unversioned process-timer payload changed | deploy backward-compatible firers first |

`AggGuardTightened` prints a **paste-ready** `replay-only` twin whose guard is the removed region
`old ∧ ¬new`, with negation eliminated inside the guard grammar (De Morgan, comparison flipping,
`x == false` for a bare boolean atom). It is printed, never auto-applied.

### `--emit-goldens DIR`

Writes old-shape payload fixtures for every event version bump in the diff — the one moment when both
the old and new wire shapes are knowable. It **never overwrites an existing file**, so a hand-captured
genuine production payload always beats a synthesized one.

### `--replay-impact-out FILE`

`diff` always prints the replay-impact verdict; this flag also writes it as stable JSON:

```json
{"verdict":"replay-neutral"}
```

```json
{"verdict":"affected",
 "aggregates":{"Reservation":{"eventTypes":["TransferReservationCreated"],
                              "includeSnapshotStreams":true}}}
```

New aggregates, events, transitions, and syntactically proven guard loosenings are replay-neutral. A
removed or changed old transition affects the event types either side emits; a changed decode surface
affects that event type directly; `includeSnapshotStreams` is set whenever the fold itself can change.
Affected event arrays are sorted. Feed the file to
[`Keiro.ReplayAudit`](/docs/keiro/reference/replay-audit).

## CI gates

```bash
keiro-dsl check service.keiro --coverage-report coverage.json
keiro-dsl scaffold service.keiro --out generated --goldens golden-payloads
cabal test your-generated-harness-component
keiro-dsl diff --since origin/main \
  --emit-goldens golden-payloads \
  --replay-impact-out replay-impact.json \
  --report-out diff-report.json \
  --coverage-report coverage.json --fail-on-opaque-increase \
  service.keiro
```

`check` proves current validity. Scaffold proves the generated plan is safe. The harness proves
hand-owned behavior agrees with generated facts *and* that supplied old payloads still decode — and,
for a spec with structural mapped types, that both binding laws hold, that the declared codec policy
and current payload goldens match, that enum/union/optional fixtures are covered, that canonical
projection witnesses agree, and that **forward stepping and replay reach equal state** over every
mapped and scalar register. `diff` proves the upgrade does not contain an unapproved breaking
persistence or identity change on any gated surface, and `--fail-on-opaque-increase` ratchets opacity
in one direction.

None of them reads your database. When the verdict is `affected`, the deploy gate is the
[real-log replay audit](/docs/keiro/how-to/audit-real-logs-before-a-deploy).
