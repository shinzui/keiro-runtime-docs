`Store` is kiroku's core capability, modelled as an `effectful` **dynamic effect**. Application
code calls the smart-constructor operations below in `Eff es` with a `Store :> es` constraint;
an interpreter supplies the actual PostgreSQL-backed behaviour (or a mock, in tests). This page
lists every operation's exact signature and the shipped interpreters.

## The effect

```haskell
data Store :: Effect where
  AppendToStream      :: StreamName -> ExpectedVersion -> [EventData] -> Store m AppendResult
  AppendMultiStream   :: [(StreamName, ExpectedVersion, [EventData])] -> Store m [AppendResult]
  ReadStreamForward   :: StreamName -> StreamVersion -> Int32 -> Store m (Vector RecordedEvent)
  ReadStreamBackward  :: StreamName -> StreamVersion -> Int32 -> Store m (Vector RecordedEvent)
  ReadAllForward      :: GlobalPosition -> Int32 -> Store m (Vector RecordedEvent)
  ReadAllBackward     :: GlobalPosition -> Int32 -> Store m (Vector RecordedEvent)
  ReadCategoryForward :: CategoryName -> GlobalPosition -> Int32 -> Store m (Vector RecordedEvent)
  GetStream           :: StreamName -> Store m (Maybe StreamInfo)
  LookupStreamId      :: StreamName -> Store m (Maybe StreamId)
  EventExistsInStream :: StreamName -> EventId -> Store m Bool
  LookupStreamNames   :: [StreamId] -> Store m (Map StreamId StreamName)
  LinkToStream        :: StreamName -> [EventId] -> Store m LinkResult
  FindEvents          :: EventFilter -> Store m (Vector RecordedEvent)
  SoftDeleteStream    :: StreamName -> Store m (Maybe StreamId)
  HardDeleteStream    :: StreamName -> Store m (Maybe StreamId)
  UndeleteStream      :: StreamName -> Store m (Maybe StreamId)
  SetStreamTruncateBefore :: StreamName -> StreamVersion -> Store m (Maybe StreamId)
  GetVisibleGlobalHeadPosition :: Store m GlobalPosition
  GetSubscriptionCheckpointInventory :: Store m SubscriptionCheckpointInventory
  InitializeSubscriptionCheckpoint ::
    SubscriptionName -> Int32 -> MissingCheckpointPolicy ->
    Store m (Either SubscriptionCheckpointMissing CheckpointInitialization)
  AcquireHistoryRetentionLease :: HistoryRetentionLeaseRequest -> Store m HistoryRetentionLease
  RenewHistoryRetentionLease ::
    HistoryRetentionLeaseHandle -> HistoryRetentionLeaseDuration ->
    Store m (Either HistoryRetentionRenewalError HistoryRetentionLease)
  ReleaseHistoryRetentionLease :: HistoryRetentionLeaseHandle -> Store m HistoryRetentionReleaseResult
  GetHistoryRetentionLeaseInventory ::
    HistoryRetentionInventoryQuery -> Store m (Vector HistoryRetentionLease)
  PruneHistoryRetentionLeases :: UTCTime -> Store m HistoryRetentionPruneResult
  RunTransaction        :: Tx.Transaction a -> Store m a
  RunTransactionNoRetry :: Tx.Transaction a -> Store m a
type instance DispatchOf Store = Dynamic
```

<Callout type="info">
  The effect is **dynamic** and its sums are **closed** by design, so downstream code can supply a
  pure in-memory interpreter in tests. The only *shipped* backend is `runStorePool` over
  `hasql-pool`.
</Callout>

<Callout type="warn">
  **Breaking across kiroku-store 0.4 → 0.7.** The effect gained **eight** constructors in four
  releases, and an exhaustive custom or mock interpreter must add an arm for each:

  | Release | Added |
  |---|---|
  | `0.4` | `GetSubscriptionCheckpointInventory` |
  | `0.5` | `InitializeSubscriptionCheckpoint` |
  | `0.6` | `GetVisibleGlobalHeadPosition` |
  | `0.7` | `AcquireHistoryRetentionLease`, `RenewHistoryRetentionLease`, `ReleaseHistoryRetentionLease`, `GetHistoryRetentionLeaseInventory`, `PruneHistoryRetentionLeases` |

  `KirokuEvent` and `StoreError` also gained constructors — see the sections below.
</Callout>

## The visible head

*(New in kiroku-store 0.6.0.0.)*

```haskell
visibleGlobalHeadPosition :: (Store :> es) => Eff es GlobalPosition
```

Returns the greatest global position still **visible** in `$all`, or zero when no event remains,
through a payload-free scalar query. No event payload is read and the configured decode hook is not
invoked.

<Callout type="warn">
  **The visible head can regress; the authoritative append frontier cannot.** Hard-deleting the
  visible tail lowers this value, while the append counter stays monotonic. That is precisely why the
  two are separate operations: use the append counter for capacity and audit reporting, and the
  visible head for anything a reader must actually be able to reach — consistency waits and
  projection distance among them.
</Callout>

## Subscription checkpoints

*(New in kiroku-store 0.4.0.0 and 0.5.0.0.)*

```haskell
subscriptionCheckpointInventory :: (Store :> es) => Eff es SubscriptionCheckpointInventory

initializeSubscriptionCheckpoint ::
  (Store :> es) =>
  SubscriptionName -> Int32 -> MissingCheckpointPolicy ->
  Eff es (Either SubscriptionCheckpointMissing CheckpointInitialization)
```

`subscriptionCheckpointInventory` returns the captured global store position and every persisted,
member-aware subscription checkpoint from **one prepared statement snapshot**, ordered by
subscription name then consumer-group member, and remains available after a worker stops. The public
`SubscriptionCheckpoint` and `SubscriptionCheckpointInventory` records expose the durable position,
member, last upsert time, and captured store position without importing Hasql or querying
Kiroku-owned tables.

`initializeSubscriptionCheckpoint` resolves an **absent** exact `(name, member)` checkpoint through a
closed policy:

<TypeTable
  type={{
    FromBeginning: { type: "MissingCheckpointPolicy", default: "default", description: "Durably seeds zero, so the subscription replays all history." },
    FromCurrentHead: { type: "MissingCheckpointPolicy", description: "Atomically seeds the current $all position, skipping all history." },
    FailIfMissing: { type: "MissingCheckpointPolicy", description: "Refuses startup with SubscriptionCheckpointMissing before any handler delivery." },
  }}
/>

Existing rows **always win**, and concurrent initializers converge on one value.

<Callout type="warn">
  **Breaking in kiroku-store 0.5.0.0.** `SubscriptionConfigM` gained `missingCheckpointPolicy`,
  defaulting to `FromBeginning` in `defaultSubscriptionConfig`. Exhaustive record literals must
  choose a policy or switch to the smart constructor. `KirokuEvent` gained
  `KirokuEventSubscriptionCheckpointResolved` and `KirokuEventSubscriptionCheckpointMissing`.
</Callout>

Keiro surfaces this policy as the `checkpoint-on-missing` clause on a `projection-owner` — see
[keiro-dsl domain and read-side nodes](/docs/keiro/reference/keiro-dsl-domain-nodes).

## History retention leases

*(New in kiroku-store 0.7.0.0.)* `Kiroku.Store.HistoryRetention` and
`Kiroku.Store.HistoryRetention.Types` expose validated, durable, **database-time-derived** leases
that protect history for the duration of a long rebuild.

```haskell
acquireHistoryRetentionLease :: (Store :> es) => HistoryRetentionLeaseRequest -> Eff es HistoryRetentionLease
renewHistoryRetentionLease   :: (Store :> es) => HistoryRetentionLeaseHandle -> HistoryRetentionLeaseDuration -> Eff es (Either HistoryRetentionRenewalError HistoryRetentionLease)
releaseHistoryRetentionLease :: (Store :> es) => HistoryRetentionLeaseHandle -> Eff es HistoryRetentionReleaseResult
historyRetentionLeaseInventory :: (Store :> es) => HistoryRetentionInventoryQuery -> Eff es (Vector HistoryRetentionLease)
pruneHistoryRetentionLeases  :: (Store :> es) => UTCTime -> Eff es HistoryRetentionPruneResult
```

Transaction combinators and mockable effect wrappers share the same owner-aware acquire, renew,
release, bounded inventory, and terminal-row pruning semantics.

```haskell
lockStreamHistoryForReplayTx :: StreamName -> Tx.Transaction ()
readStreamForwardTx          :: StreamName -> StreamVersion -> Int32 -> Tx.Transaction (Vector RecordedEvent)
```

`lockStreamHistoryForReplayTx` holds a transaction-scoped stream guard, and `readStreamForwardTx`
reads exact ordered history in that same transaction. Append, link, lifecycle mutation, and every
supported hard delete affecting the stream **serialize behind the guard**.

<Callout type="warn">
  **`StoreError` gained `HistoryRetentionActive`**, returned when a supported hard delete is refused
  by an active lease. Supported hard delete now checks retention *before* mutation and locks every
  affected stream in ascending stream-ID order — including streams that merely contain **links** to
  target-originated events. `KirokuEvent` gained committed acquisition, renewal, release, pruning,
  and hard-delete-conflict events.
</Callout>

This is the mechanism Keiro's
[versioned projection rebuilds](/docs/keiro/reference/versioned-rebuilds) use to keep replay history
alive across a long convergence. Kiroku migration `0010` supplies the lease table.

## Append

```haskell
appendToStream    :: (HasCallStack, Store :> es) => StreamName -> ExpectedVersion -> [EventData] -> Eff es AppendResult
appendMultiStream :: (HasCallStack, Store :> es) => [(StreamName, ExpectedVersion, [EventData])] -> Eff es [AppendResult]
```

`appendToStream` appends a non-empty batch to one stream under an `ExpectedVersion` guard;
all-or-nothing per call, read-your-own-writes on the same handle. It rejects `$all` with
`ReservedStreamName`, names longer than 512 UTF-8 bytes with `StreamNameTooLong`, and `[]` with
`EmptyAppendBatch` before database work. On transient serialization failures the interpreter retries
the single statement once with the same prepared event ids.

`appendMultiStream` appends to several streams in one transaction, pre-locking streams in
`stream_id` order for existing rows. Fresh streams are not pre-locked, so a concurrent
single-stream append can still create a source/`$all` deadlock cycle. PostgreSQL rolls back one
transaction; a repeated conflict after the store retry surfaces as `TransientTransactionFailure`. An empty operation list returns `[]` without
a round trip. If any per-stream event list is empty, or any target stream name is invalid, the whole
call is rejected before the transaction opens. The result list mirrors input order.

## Read

```haskell
readStreamForward       :: (HasCallStack, Store :> es) => StreamName -> StreamVersion -> Int32 -> Eff es (Vector RecordedEvent)
readStreamForwardStream :: (HasCallStack, Store :> es) => StreamName -> StreamVersion -> Int32 -> Stream (Eff es) RecordedEvent
readStreamBackward      :: (HasCallStack, Store :> es) => StreamName -> StreamVersion -> Int32 -> Eff es (Vector RecordedEvent)
readAllForward          :: (HasCallStack, Store :> es) => GlobalPosition -> Int32 -> Eff es (Vector RecordedEvent)
readAllBackward         :: (HasCallStack, Store :> es) => GlobalPosition -> Int32 -> Eff es (Vector RecordedEvent)
readCategory            :: (HasCallStack, Store :> es) => CategoryName -> GlobalPosition -> Int32 -> Eff es (Vector RecordedEvent)
```

Cursors are **exclusive**: `StreamVersion 0` / `GlobalPosition 0` read from the start (for
backward reads, `0` means "after everything"), and the `$all` seed row (position 0) is never
returned. A nonzero backward cursor is an exclusive upper bound: pass the oldest version/position
from one descending page to fetch the next older page without repeating the boundary event. The
final `Int32` is the batch/page size. `readStreamForwardStream` is a Streamly constant-memory paging
variant (suggested page size 256).

Ordered per-stream reads honor the stream's logical `truncateBefore` marker: events whose
per-stream version is lower than the marker are hidden from `readStreamForward`,
`readStreamBackward`, and `readStreamForwardStream`. `$all`, category reads, subscriptions,
causation/correlation queries, and existence probes ignore the marker and keep seeing full history.

## Stream lookups

```haskell
getStream         :: (HasCallStack, Store :> es) => StreamName -> Eff es (Maybe StreamInfo)
lookupStreamId    :: (HasCallStack, Store :> es) => StreamName -> Eff es (Maybe StreamId)
lookupStreamNames :: (HasCallStack, Store :> es) => [StreamId] -> Eff es (Map StreamId StreamName)
lookupStreamName  :: (HasCallStack, Store :> es) => StreamId   -> Eff es (Maybe StreamName)
eventExistsInStream :: (HasCallStack, Store :> es) => StreamName -> EventId -> Eff es Bool
```

`getStream` returns `StreamInfo` (id, name, version, timestamps, and `truncateBefore`) for live and
soft-deleted streams, or `Nothing` if the stream never existed or was hard-deleted.
`lookupStreamNames` is the **batch** inverse used by fan-in reads (see ADR 0001).
`eventExistsInStream` is the point lookup for idempotency checks: it returns `True` only when the
event id is linked into the supplied live stream, and `False` for another stream, a missing event, a
missing stream, or a soft-deleted stream.

## Link

```haskell
linkToStream :: (Store :> es) => StreamName -> [EventId] -> Eff es LinkResult
```

Shares existing events into another stream without copying their payload; the linked event keeps
its original `globalPosition`. `LinkResult` carries no `globalPosition` because linking does not
advance `$all`.

## Lifecycle

```haskell
softDeleteStream :: (HasCallStack, Store :> es) => StreamName -> Eff es (Maybe StreamId)
hardDeleteStream :: (HasCallStack, Store :> es) => StreamName -> Eff es (Maybe StreamId)
undeleteStream   :: (HasCallStack, Store :> es) => StreamName -> Eff es (Maybe StreamId)
setStreamTruncateBefore   :: (HasCallStack, Store :> es) => StreamName -> StreamVersion -> Eff es (Maybe StreamId)
clearStreamTruncateBefore :: (HasCallStack, Store :> es) => StreamName -> Eff es (Maybe StreamId)
```

All return `Nothing` when the stream is not found (a no-op) and reject `$all`. `softDeleteStream`
keeps events in `$all`; `hardDeleteStream` is GUC-gated (`kiroku.enable_hard_deletes`),
irreversible, and intended for GDPR erasure; `undeleteStream` reverses a soft delete.

`setStreamTruncateBefore name version` sets a reversible logical marker for close-the-book
compaction. Future ordered per-stream reads hide events below `version`, while `$all`, category
reads, subscriptions, and projections still see full history. `clearStreamTruncateBefore` sets the
marker back to `StreamVersion 0`. See [the append-only log](/docs/kiroku/explanation/append-only-log)
and [Close the book on a stream](/docs/kiroku/how-to/close-the-book-on-a-stream).

## Causation / correlation

```haskell
findCausationDescendants :: (Store :> es) => EventId -> Eff es (Vector RecordedEvent)
findCausationAncestors   :: (Store :> es) => EventId -> Eff es (Vector RecordedEvent)
findByCorrelation        :: (Store :> es) => UUID    -> Eff es (Vector RecordedEvent)
```

Graph walks over the `causation_id` / `correlation_id` columns. The same selection is available
declaratively through the effect's `FindEvents` op with an `EventFilter`.

## Transactions (escape hatch)

```haskell
RunTransaction        :: Tx.Transaction a -> Store m a   -- BEGIN/COMMIT with serialization retry
RunTransactionNoRetry :: Tx.Transaction a -> Store m a   -- exactly-once body, no retry
```

Run an explicit `hasql` transaction through the store's pool — for example to append events _and_
update an inline projection table atomically. `RunTransaction` retries the body on serialization
failure; `RunTransactionNoRetry` runs it exactly once. Connection and server failures are mapped to
typed `StoreError` constructors where the store can recognise them. A duplicate event constraint
becomes `DuplicateEvent (Just eventId)` when its detail is parseable. PostgreSQL `40001` and `40P01` preserve their code/message as `TransientTransactionFailure`
(retryable) since Kiroku 0.8. Other server failures preserve
their SQLSTATE and message as `UnexpectedServerError`; they are not misclassified as a missing
`<transaction>` stream.

## Interpreters

```haskell
runStorePool     :: (IOE :> es, Error StoreError :> es) => KirokuStore -> Eff (Store : es) a -> Eff es a
runStoreIO       :: KirokuStore -> Eff (Store : Error StoreError : IOE : '[]) a -> IO (Either StoreError a)
runStoreResource :: KirokuStore -> Eff (Store : es) a -> Eff es a   -- resourcet-scoped
```

`runStorePool` is the shipped backend over `hasql-pool`, layering the `Store` effect onto an
existing stack that already provides `IOE` and `Error StoreError`. `runStoreIO` is the
convenience runner that discharges everything to `IO (Either StoreError a)` — the one used in the
tutorials. `runStoreResource` is the `resourcet`-scoped variant.

<Callout type="warn">
  Open the store (and run migrations) **before** interpreting any `Store` effect: interpreters use
  the pool inside `KirokuStore`, which `withStore` acquires. The store never runs DDL.
</Callout>

## The store resource

`Kiroku.Store.Effect.Resource` carries the acquired handle itself, so code deeper in the stack can
retrieve it without it being threaded through every call:

```haskell
data KirokuStoreResource :: Effect
type instance DispatchOf KirokuStoreResource = Static WithSideEffects

getKirokuStore :: (KirokuStoreResource :> es) => Eff es KirokuStore

withKirokuStore ::
  (IOE :> es) => ConnectionSettings -> Eff (KirokuStoreResource : es) a -> Eff es a

runKirokuStoreWith ::
  (IOE :> es) => KirokuStore -> Eff (KirokuStoreResource : es) a -> Eff es a
```

It is a **static** effect, deliberately: the handle is acquired once per program and is not meant
to be mocked — the mocking surface is the dynamic `Store` effect above, which operates *against* the
handle. It is `Static WithSideEffects` rather than `Static NoSideEffects` because the pool performs
IO during operation lookup.

The two runners differ only in who owns the handle's lifetime:

| Runner | Acquires / releases | Use when |
|---|---|---|
| `withKirokuStore` | yes — brackets `withStore` | the action *is* the program's store scope |
| `runKirokuStoreWith` | no — the caller owns the handle | you already hold an open store and run several independent actions against it |

<Callout type="info">
  `runKirokuStoreWith` (kiroku-store **0.3.1.0**) exists to stop callers paying for acquisition per
  action. Each `withKirokuStore` costs a connection pool, a dedicated `LISTEN` connection, and a
  publisher thread; a process that opens exactly one store — the arrangement this effect is designed
  for — should acquire once and install the handle repeatedly.

  It still requires `IOE` despite neither bracketing nor unlifting, because `evalStaticRep` demands
  `IOE` for any `Static WithSideEffects` effect.
</Callout>

Keiro's transactional command runners require this effect; see
[the Command reference](/docs/keiro/reference/command).
