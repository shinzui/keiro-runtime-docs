title: "04 — The reservation workflow"
description: "A durable workflow: hold a bed, park on an awakeable awaiting confirmation, then release-or-retain and summarize."
---

The reservation workflow journals a transfer hold, waits for confirmation, then decides whether
to release or retain capacity. It is separate from the reservation aggregate and local PGMQ work.

## The procedure

From `mori://shinzui/keiro-runtime-jitsurei`, project-relative path `services/hospital-capacity/src/HospitalCapacity/ReservationWorkflow.hs`
(artifact-level URI pending):

```haskell
reservationWorkflow
  :: (Workflow :> es, Store :> es, IOE :> es)
  => ReservationWorkflowInput
  -> Eff es ReservationWorkflowSummary
reservationWorkflow input = do
  hold <- step (StepName "create-transfer-hold") (createTransferHold input)
  (_awakeableId, awaitConfirmation) <- awakeableNamed (StepName "reservation-confirmation")
  confirmation <- awaitConfirmation
  release <- step (StepName "release-or-retain-capacity") (releaseOrRetainCapacity input confirmation)
  step (StepName "summarize-reservation") (summarizeReservation input hold confirmation release)
```

Names are durable step keys. A resumed run reuses completed results and continues through the
confirmation wait; changing a stored result type requires a deliberate workflow evolution.

## Signal by owner

From `mori://shinzui/keiro-runtime-jitsurei`, project-relative path `services/hospital-capacity/src/HospitalCapacity/Store.hs`
(artifact-level URI pending):

```haskell
signalReservationConfirmationWithTelemetry :: ServiceTracer -> HospitalCapacityStore -> TransferReservationId -> ReservationConfirmation -> IO (Either StoreError Bool)
signalReservationConfirmationWithTelemetry tracer store reservationId confirmation =
  withApplicationSpan
    tracer
    "hospital-capacity.workflow signal reservation-confirmation"
    ( baseAttributes
        <> [ ("emergency.reservation.id", showText reservationId)
           , ("emergency.confirmation.id", confirmation.confirmationId)
           ]
    ) $
  runHospitalCapacityStore store $
    findPendingReservationAwakeable reservationId >>= \case
      Nothing -> pure False
      Just awakeableId -> signalAwakeable awakeableId confirmation

selectPendingWorkflowAwakeableStmt :: Statement (Text, Text) (Maybe UUID.UUID)
selectPendingWorkflowAwakeableStmt =
  preparable
    """
    SELECT awakeable_id
    FROM keiro.keiro_awakeables
    WHERE owner_workflow_name = $1
      AND owner_workflow_id = $2
      AND status = 'pending'
    ORDER BY created_at DESC
    LIMIT 1
    """
    ( contrazip2
        (E.param (E.nonNullable E.text))
        (E.param (E.nonNullable E.text))
    )
    (D.rowMaybe (D.column (D.nonNullable D.uuid)))
```

The lookup uses workflow owner name/ID and `pending` status, then signals the stored opaque ID.
The application does not reconstruct that ID using its historical helper. A missing pending wait
returns `False`; the caller must not claim a signal occurred. After signalling, another workflow
run can complete the remaining steps.
