---
title: "03 — The surge process manager"
description: "The surge process manager that reacts to capacity pressure, activates surge, and schedules a follow-up timer."
---

The surge manager reacts to pressure with durable memory, a target Hospital command, and a
follow-up timer. Its generated process facts describe the topology; hand-owned code determines
when the observation warrants action.

## Process action

From `mori://shinzui/keiro-runtime-jitsurei`, project-relative path `services/hospital-capacity/src/HospitalCapacity/SurgeManager.hs`
(artifact-level URI pending):

```haskell
hospitalSurgeProcessManager :: HospitalSurgeProcessManager
hospitalSurgeProcessManager =
  ProcessManager
    { name = hospitalSurgeProcessName
    , correlate = \input -> idText input.hospitalId
    , eventStream = surgeEventStream
    , streamFor = surgeStream . mustHospitalIdText
    , targetEventStream = hospitalEventStream
    , targetProjections = const [hospitalReadinessProjection]
    , handle = \input ->
        let timer = surgeTimerRequest input.hospitalId (surgeDeadline input.observedAt)
         in ProcessManagerAction
              { command =
                  NoteSurgeThreshold
                    NoteSurgeThresholdData
                      { hospitalId = input.hospitalId
                      , availableIcuBeds = input.availableIcuBeds
                      , redDemand = input.redDemand
                      , timerId = timerIdText timer.timerId
                      }
              , commands =
                  [ PMCommand
                      { target = hospitalCommandStream input.hospitalId
                      , command =
                          ActivateSurge
                            ActivateSurgeData
                              { hospitalId = input.hospitalId
                              , commandId = placeholderCommandId
                              }
                      }
                  ]
              , timers = [timer]
              }
    }
```

The source correlates by hospital, records `NoteSurgeThreshold` in its own stream, dispatches
`ActivateSurge` to the validated Hospital stream, and schedules a timer. The process runtime owns
command dispatch identity; the placeholder in the action is not a fresh identity generator.
The target readiness projection runs with the target append.

## Identity and replay

From `mori://shinzui/keiro-runtime-jitsurei`, project-relative path `services/hospital-capacity/src/HospitalCapacity/SurgeManager.hs`
(artifact-level URI pending):

```haskell
surgeStream :: HospitalId -> Stream SurgeEventStreamDef
surgeStream hospitalId = Stream.entityStream Generated.hospitalSurgeCategory (idText hospitalId)
```

The generated checked category feeds `entityStream`. Timer redelivery and process replays must
retain their original command identities; replay tests in the service verify clean re-execution.
Use the durable regional-surge scenario to observe the persisted process and timer outcome.
