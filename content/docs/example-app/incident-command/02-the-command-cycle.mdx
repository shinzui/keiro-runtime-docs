The write path accepts an `IncidentCommandStore`, a command ID, and a **validated** event
stream. The command ID determines event identities, so retrying the same command does not
mint an unrelated set of events. This chapter follows the committed application at `e3c800e`.

## The aggregate entrypoint

From `mori://shinzui/keiro-runtime-jitsurei`, project-relative path `services/incident-command/src/IncidentCommand/Incident/CommandProcessor.hs`
(artifact-level URI pending):

```haskell
runIncidentCommandDurablyWithTelemetry :: ServiceTracer -> IncidentCommandStore -> IncidentId -> IncidentCommand -> IO (Either CommandFailure CommandSuccess)
runIncidentCommandDurablyWithTelemetry tracer store incidentId command =
  withApplicationSpan
    tracer
    "incident-command.command processor incident"
    (incidentCommandAttributes incidentId command) $
    runDurableCommand tracer store (incidentCommandId command) incidentEventStream (incidentStream incidentId) command [incidentDashboardProjection]
```

The application span encloses the command. `incidentCommandId` extracts the typed identity,
`incidentStream` supplies the category-derived target, and the dashboard projection is passed
explicitly. FieldResource and Triage use the same service runner with their own validated streams.

## One shared runner

From `mori://shinzui/keiro-runtime-jitsurei`, project-relative path `services/incident-command/src/IncidentCommand/Store.hs`
(artifact-level URI pending):

```haskell
runDurableCommand
  :: (BoolAlg phi (RegFile rs, ci), Eq co)
  => ServiceTracer
  -> IncidentCommandStore
  -> CommandId
  -> ValidatedEventStream phi rs s ci co
  -> Stream (EventStream phi rs s ci co)
  -> ci
  -> [InlineProjection co]
  -> IO (Either CommandFailure CommandSuccess)
runDurableCommand tracer store commandId eventStream targetStream command projections = do
  result <-
    runIncidentCommandStore store $
      runCommandWithProjections (commandOptionsWithId tracer commandId) eventStream targetStream command projections
  pure $
    case result of
      Left storeError -> Left (CommandStoreFailed storeError)
      Right (Left commandError) -> Left (CommandProcessorFailed commandError)
      Right (Right commandResult) -> Right (toCommandSuccess commandResult)
```

`runIncidentCommandStore` interprets the resource-backed static Store effect and its typed errors.
Keiro hydrates and replays the target, transduces the command, then appends events and runs the
supplied inline projections transactionally. The outer `Left` maps to `CommandStoreFailed`;
the inner command failure maps to `CommandProcessorFailed`.

## Stable event IDs

From `mori://shinzui/keiro-runtime-jitsurei`, project-relative path `services/incident-command/src/IncidentCommand/Store.hs`
(artifact-level URI pending):

```haskell
commandOptionsWithId :: ServiceTracer -> CommandId -> RunCommandOptions
commandOptionsWithId tracer commandId =
  (commandOptionsWithTelemetry tracer)
    { Command.eventIds = deterministicCommandEventIds commandId
    }

deterministicCommandEventIds :: CommandId -> [EventId]
deterministicCommandEventIds commandId =
  [ EventId
      ( UUID.V5.generateNamed
          UUID.V5.namespaceURL
          (fmap (fromIntegral . fromEnum) (Text.unpack (seed eventIndex)))
      )
  | eventIndex <- [0 :: Int ..]
  ]
 where
  seed eventIndex =
    "incident-command:event:" <> showText commandId <> ":" <> Text.pack (show eventIndex)
```

The stream of UUIDv5 values is keyed by command identity and event ordinal. The same command
therefore proposes the same event IDs on retry. This is the application's identity convention,
not permission to treat every duplicate in an unrelated stream as success.
