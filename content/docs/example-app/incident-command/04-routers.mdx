Incident Command has two hand-owned routers. Generated Router/RouterHarness modules capture
checked topology, while the application keeps its composite resource key and SQL target selection.
A router stores no independent process state; it resolves target commands from accepted input.

## Resource dispatch

From `mori://shinzui/keiro-runtime-jitsurei`, project-relative path `services/incident-command/src/IncidentCommand/ResourceRouter.hs`
(artifact-level URI pending):

```haskell
resourceDispatchRouter
  :: (IOE :> es, Store :> es)
  => Router ResourceDispatchedData (HsPred FieldResourceRegs FieldResourceCommand)
       FieldResourceRegs FieldResourceVertex FieldResourceCommand FieldResourceEvent es
resourceDispatchRouter =
  Router
    { name = "incident-command-resource-dispatch"
    , key = \dispatched -> showText dispatched.incidentId <> ":" <> showText dispatched.resourceId
    , resolve = \dispatched -> do
        result <- runQuery Nothing fieldResourceAssignmentReadModel (FieldResourceAssignmentQuery dispatched.resourceId)
        pure $
          case result of
            Right (Just assignment)
              | assignmentTargetsIncident dispatched assignment ->
                  [ PMCommand
                      { target = fieldResourceCommandStream dispatched.resourceId
                      , command =
                          AssignResource
                            AssignResourceData
                              { resourceId = dispatched.resourceId
                              , commandId = dispatched.commandId
                              , incidentId = dispatched.incidentId
                              }
                      }
                  ]
            _ -> []
    , targetEventStream = fieldResourceEventStream
    , targetProjections = const [fieldResourceAssignmentProjection]
    }
```

The key combines incident and resource identity. The resolver reads the assignment view, checks
that it targets the intended incident, and returns a typed `PMCommand` for FieldResource. A missing
or unsuitable assignment produces no commands. The validated target stream and inline projection
are supplied with the router, so dispatch uses the normal command boundary.

## Capacity changes

From `mori://shinzui/keiro-runtime-jitsurei`, project-relative path `services/incident-command/src/IncidentCommand/CapacityChangeRouter.hs`
(artifact-level URI pending):

```haskell
capacityChangeRouter
  :: (IOE :> es, Store :> es)
  => Router AcceptedHospitalCapacitySnapshot (HsPred IncidentRegs IncidentCommand)
       IncidentRegs IncidentVertex IncidentCommand IncidentEvent es
capacityChangeRouter =
  Router
    { name = "incident-command-capacity-change"
    , key = \snapshot -> snapshot.messageId
    , resolve = \snapshot -> do
        result <- resolveCapacityIncidentCandidates snapshot
        case result of
          Left _ -> pure []
          Right candidates ->
            pure (rights (capacityChangeCommandForCandidate snapshot <$> candidates))
    , targetEventStream = incidentEventStream
    , targetProjections = const [incidentDashboardProjection]
    }
```

The accepted hospital snapshot's message ID is the routing key. Candidate selection and command
construction remain hand-owned; they are not replaced by a CLI dispatcher. The integration inbox
supplies the accepted snapshot, and replay safety depends on deterministic target-command identity
and the runtime's benign-duplicate checks.
