title: "03 — Read models and projections"
description: "The dashboard, evacuation-zone, and audit read models, and the difference between inline and async projection."

Incident Command registers six read models. Generated declarations supply identity, schema,
version, shape, and consistency facts; hand-owned projection modules supply application queries
and event-to-SQL updates. Inline delivery does not make a model's declared consistency `Strong`.

## Read the generated contract first

From `mori://shinzui/keiro-runtime-jitsurei`, project-relative path `services/incident-command/src/IncidentCommand/Incident_dashboard/Generated/ReadModel.hs`
(artifact-level URI pending):

```haskell
incidentDashboardReadModel :: ReadModel IncidentDashboardQueryInput IncidentDashboardQueryResult
incidentDashboardReadModel =
  ReadModel
    { name = "incident-command-incident-dashboard"
    , tableName = "incident_dashboard"
    , schema = "incident_command"
    , subscriptionName = "incident-command-dashboard-inline"
    , version = 1
    , shapeHash = "fnv1a:9d42f7941cb4eb1a"
    , defaultConsistency = Eventual
    , strongScope = EntireLog
    , query = incidentDashboardQuery
    }
```

The dashboard explicitly declares `Eventual`, names the `incident_command` schema, and carries a
shape hash. `EntireLog` is the scope field, not a promise of strong query freshness. The hand-owned
wrapper preserves those generated facts while substituting its typed query:

From `mori://shinzui/keiro-runtime-jitsurei`, project-relative path `services/incident-command/src/IncidentCommand/Incident/Projection.hs`
(artifact-level URI pending):

```haskell
incidentDashboardReadModel :: ReadModel IncidentDashboardQuery (Maybe IncidentDashboard)
incidentDashboardReadModel =
  ReadModel
    { name = GeneratedDashboard.incidentDashboardReadModel.name
    , tableName = GeneratedDashboard.incidentDashboardReadModel.tableName
    , schema = GeneratedDashboard.incidentDashboardReadModel.schema
    , subscriptionName = GeneratedDashboard.incidentDashboardReadModel.subscriptionName
    , version = GeneratedDashboard.incidentDashboardReadModel.version
    , shapeHash = GeneratedDashboard.incidentDashboardReadModel.shapeHash
    , defaultConsistency = GeneratedDashboard.incidentDashboardReadModel.defaultConsistency

        Tx.statement (idText incidentId) selectIncidentDashboardStmt
    }
```

## Delivery and registration

The command entrypoint still passes `incidentDashboardProjection` as an inline projection.
Its `applyIncidentEvent` updates dashboard/evacuation rows and command audit inside the append
transaction. Separate async projection drivers can drain or rebuild the views from subscriptions;
readers must not infer a global strong-consistency guarantee from the existence of the inline helper.

From `mori://shinzui/keiro-runtime-jitsurei`, project-relative path `services/incident-command/src/IncidentCommand/Store.hs`
(artifact-level URI pending):

```haskell
registerIncidentCommandReadModels :: Store :> es => Eff es ()
registerIncidentCommandReadModels =
  mapM_ register
    [ readModelRegistration incidentDashboardReadModel
    , readModelRegistration evacuationZoneReadModel
    , readModelRegistration fieldResourceAssignmentReadModel
    , readModelRegistration pendingTransferNeedsReadModel
    , readModelRegistration commandAuditReadModel
    , readModelRegistration capacityIncidentCandidateReadModel
    ]
 where
  register (modelName, modelVersion, modelShapeHash) =
    void (registerReadModel modelName modelVersion modelShapeHash)
```

The six views are dashboard, evacuation zones, resource assignments, transfer needs, command audit,
and capacity-change candidates. Startup registers each stable name/version/shape and checks the
registration. The worker's `projections once` and `projections rebuild` are the operational paths
for async progress and reconstruction.

See [projection reference](/docs/keiro/reference/projection), then continue to
[routers](/docs/example-app/incident-command/04-routers).
