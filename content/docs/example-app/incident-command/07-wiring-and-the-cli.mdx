`Store.hs` owns a process-level resource runner shared by commands, routers, processes, workflows,
inbox, and outbox entrypoints. It opens one Kiroku resource scope, rather than one pool per command.

## Resource lifetime

From `mori://shinzui/keiro-runtime-jitsurei`, project-relative path `services/incident-command/src/IncidentCommand/Store.hs`
(artifact-level URI pending):

```haskell
newtype IncidentCommandStore = IncidentCommandStore
  (forall a. Eff '[Store, Error StoreError, KirokuStoreResource, IOE] a -> IO (Either StoreError a))

runIncidentCommandStore
  :: IncidentCommandStore
  -> Eff '[Store, Error StoreError, KirokuStoreResource, IOE] a
  -> IO (Either StoreError a)
runIncidentCommandStore (IncidentCommandStore runner) = runner

withIncidentCommandStore :: (IncidentCommandStore -> IO a) -> IO a
withIncidentCommandStore action = do
  connString <- connectionStringFromEnvironment
  runEff $
    withKirokuStore (incidentConnectionSettings connString) $
      withEffToIO (ConcUnlift Persistent Unlimited) $ \unlift -> do
        let store = IncidentCommandStore (unlift . runErrorNoCallStack . runStoreResource)
        registration <- runIncidentCommandStore store registerIncidentCommandReadModels
        case registration of
          Left storeError -> fail ("failed to register Incident Command read models: " <> show storeError)
          Right () -> action store
```

The rank-n runner hides the resource stack from ordinary IO callers. It interprets `Store` and
`Error StoreError` inside `KirokuStoreResource`, registers read models before the callback, and
fails startup if registration fails. Store settings keep framework objects in `kiroku` and include
the application schema through the configured extra search path; SQL remains schema-qualified.

## Executables and evidence

The package ships CLI, worker, and migration executables. The CLI exposes commands and the
`scenario mass-casualty --durable` path. The worker drives projections, escalation timers, Kafka
inbox consumption, and outbox publishing. Kafka offers both one-shot and continuous consumption;
continuous mode shuts down the Shibuya application before closing its consumer scope.

Use service `just migration-plan/status/up/verify/check` before runtime work, root `just dsl-check`
for generated facts, and root `just test-all` for non-live tests. Read
[the worker commands](/docs/example-app/running-it/02-the-workers) for concrete invocations.
Telemetry is opt-in and the executable flushes its provider before exit.
