# Keiro Service Architecture

**Design bounded contexts, invariants, aggregates, domain events, and workflows first; express that model through the platform's service contracts and vertical slices.**

This area is the fleet structure standard for deployed keiro services. It reconciles danwa's shipped six-package, collocated module structure with the richer keiro-dsl node vocabulary in keiro-runtime-jitsurei. Danwa's code is authoritative where its older prose disagrees with it; keiro-runtime-jitsurei is the node-placement reference, but its teaching-only monolith and legacy duplicate modules are not production conventions.

## Start Here

* [Domain design and runtime choices](/docs/runtime-patterns/architecture/domain-design) establishes the business model and consistency boundaries before code layout.

* [Domain newtypes and TypeIDs](/docs/runtime-patterns/architecture/domain-newtypes-and-typeids) makes TypeID the service-owned identifier default and forbids raw primitives for key domain values.

* [Service packages](/docs/runtime-patterns/architecture/service-packages) defines the six cabal packages, their dependency boundaries, and the teaching-repository exception.

* [Vertical-slice modules](/docs/runtime-patterns/architecture/vertical-slice-modules) defines the per-concept generated and hand-owned module ring.

* [Specification and scaffolding](/docs/runtime-patterns/architecture/spec-and-scaffolding) places the single-file or workspace service contract and gives the repeatable whole-service regeneration workflow.

* [The generated compilation contract](/docs/runtime-patterns/architecture/generated-compilation-contract) states how generated Haskell must be compiled: the GHC2024 baseline, the closed module-local extension set, the runtime-package authority, and the one conformance package a configured service scaffolds.

* [Generated Haskell editions](/docs/runtime-patterns/keiro/generated-haskell-editions) governs explicit v2 adoption, record consumers, backup scope, and rollback.

* [Cross-cutting modules](/docs/runtime-patterns/architecture/cross-cutting-modules) is the closed allowlist for technical module names.

* [Extended node verticals](/docs/runtime-patterns/architecture/extended-node-verticals) places read models, process managers, workflows, routers, queues, and integration contracts.

* [Test layout](/docs/runtime-patterns/architecture/test-layout) assigns test suites to packages and mirrors source verticals in test modules.

* [Worked Conversation example](/docs/runtime-patterns/architecture/worked-example-conversation) traces one real danwa concept across every package.

## How To Use This Standard

To start a service in this platform, follow [domain design and runtime choices](/docs/runtime-patterns/architecture/domain-design). Capture business scenarios, invariant ownership, aggregate command/event behavior, and cross-context workflows. Then apply [DSL adoption](/docs/runtime-patterns/keiro/dsl-adoption), [domain newtypes and TypeIDs](/docs/runtime-patterns/architecture/domain-newtypes-and-typeids), specification and scaffolding, service packages, and vertical-slice modules. To place a keiro-dsl node beyond an aggregate, use extended node verticals. When a proposed module has a technology-shaped name rather than a domain-concept name, check the cross-cutting allowlist; if the name is absent, keep the code in the owning concept vertical.

The generated/hand-owned boundary is load-bearing. Keiro-dsl may replace every `Generated.*` module, including structural wire shapes and projection witnesses, while developers own aggregate holes, consumer bindings, fixtures, and application modules. Never copy legacy parallel modules from a teaching repository into a deployed service.
