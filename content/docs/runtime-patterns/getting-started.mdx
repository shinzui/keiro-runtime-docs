# Getting started with the runtime patterns

These standards serve one microservice platform with isolated DDD bounded contexts. Begin with domain design; package layout, generation, and transport implement the model.

Choose the task that brought you here. Each route starts with the narrowest
normative document; follow its related links or the subject overview when you
need the surrounding rules.

* **Designing a bounded context or starting a service:** begin with
  [domain design and runtime choices](/docs/runtime-patterns/architecture/domain-design): establish the
  ubiquitous language, business scenarios, invariants, aggregate boundaries,
  commands, domain events, and workflow outcomes. Choose consistency and
  cross-context contracts before arranging packages or selecting transports.

* **Turning the domain model into a service:** apply
  [DSL adoption](/docs/runtime-patterns/keiro/dsl-adoption), then
  [domain newtypes and TypeIDs](/docs/runtime-patterns/architecture/domain-newtypes-and-typeids),
  [service workspaces](/docs/runtime-patterns/keiro/service-workspaces), and the
  [six application-package standard](/docs/runtime-patterns/architecture/service-packages). Use the
  [architecture overview](/docs/runtime-patterns/architecture/overview) for module and test layout.

* **Handling business request retries:** define the
  [command request contract](/docs/runtime-patterns/keiro/command-cycle-and-errors#make-business-request-retries-explicit)
  before exposing a command endpoint.

* **Defining an aggregate:** first establish its
  [invariants, command outcomes, and domain events](/docs/runtime-patterns/architecture/domain-design),
  then use [aggregate transition ownership](/docs/runtime-patterns/keiro/aggregate-expressions).
  For hand-owned behavior, follow
  [Keiki transducer best practices](/docs/runtime-patterns/keiki/transducer-best-practices), then
  apply the [build-time validation gate](/docs/runtime-patterns/keiki/build-time-validation). Mint every
  hand-written command and event constructor through
  [trusted constructor evidence](/docs/runtime-patterns/keiki/constructor-evidence), which is also the
  upgrade path for an aggregate still calling the deprecated `mkWireCtor` family. When
  guards inspect fields of rich consumer-owned records, use the
  [typed field-projection pattern](/docs/runtime-patterns/keiki/typed-field-projections), and add
  [exact projection domains](/docs/runtime-patterns/keiki/exact-projection-domains) when a gate must
  prove something about a projected guard rather than merely execute it. When the
  aggregate is declared in a `.keiro` source, use
  [aggregate scalar expressions and transition ownership](/docs/runtime-patterns/keiro/aggregate-expressions)
  to decide what the spec generates and what stays hand-owned.

* **Writing or upgrading a `.keiro` source:** start with
  [workspace-first service contracts](/docs/runtime-patterns/keiro/service-workspaces): use one
  versioned workspace by default, keep each aggregate in a readable single-owner
  member, and reserve a bare source for a trivial domain with exactly one
  aggregate. Then read
  [Keiro DSL language versions](/docs/runtime-patterns/keiro/language-versions) to pick and declare
  Language 6 from Keiro 0.17.0.0 onward; require `--min-language 6` in CI
  and verify each source reports the adopted version. Follow
  [semantic-local regeneration](/docs/runtime-patterns/keiro/dsl-semantic-locality) and inventory
  every [mapped consumer surface](/docs/runtime-patterns/keiro/mapped-consumer-surfaces); use
  [consumer-owned nominal bindings](/docs/runtime-patterns/keiro/nominal-bindings) when existing ID,
  enum, or scalar-wrapper types must appear in checked aggregate fields; and
  [enforced identifier domains](/docs/runtime-patterns/keiro/identifier-domains) before moving a
  prefix-bearing ID onto version 3. Choose every new prefix with the
  [TypeID prefix naming standard](/docs/runtime-patterns/keiro/typeid-prefix-naming); do not impose
  an arbitrary abbreviation budget.

* **Upgrading generated Haskell or the keiro-dsl package API:** follow
  [generated Haskell editions](/docs/runtime-patterns/keiro/generated-haskell-editions) for the
  explicit migration, hand-owned record audit, Cabal reconciliation, and rollback.
  Keep this separate from the source-language declaration.

* **Proving an aggregate behaves as declared:** use
  [behavior conformance and obligations](/docs/runtime-patterns/keiro/behavior-conformance) to
  inventory every transition, rejection, and replay-only edge and gate CI on the
  generated report.

* **Adopting Keiro in an existing service:** follow
  [brownfield Keiro adoption](/docs/runtime-patterns/keiro/brownfield-adoption) to inventory stored
  bytes, map existing types, compare codecs, prove replay, and cut over without
  introducing a second wire authority.

* **Assembling the runtime:** follow
  [runtime assembly](/docs/runtime-patterns/keiro/runtime-assembly) for resource acquisition,
  validated streams, handlers, workers, and startup order. Build read-side
  ownership through [typed projection catalogs](/docs/runtime-patterns/keiro/projection-catalogs).

* **Serving and evolving the read side:** declare freshness and publish external
  SQL access through [read models and projections](/docs/runtime-patterns/keiro/read-models-and-projections);
  choose between the offline, schema-versioned, and
  [targeted stream](/docs/runtime-patterns/keiro/stream-scoped-repair) lifecycles before touching a
  serving target.

* **Protecting a long replay:** hold a
  [Kiroku replay-history retention lease](/docs/runtime-patterns/kiroku/history-retention) for the
  whole run, and abandon rather than reacquire when it lapses.

* **Inspecting or repairing a live runtime:** use the
  [Keiro operations console](/docs/runtime-patterns/keiro/operations-console) so schema checks,
  previews, stable JSON, bounded passes, and application-owned hooks wrap the
  supported lifecycle APIs. Resume a parked `Dead` timer only through
  [dead timer resume](/docs/runtime-patterns/keiro/dead-timer-resume), after the migration `0032`
  writer rollout.

* **Choosing a transport:** use the
  [transport-selection matrix](/docs/runtime-patterns/messaging/transport-selection) before adopting
  PGMQ, Kafka, or a Kiroku subscription. For PGMQ, also apply the
  [queue lifecycle and reconciliation standard](/docs/runtime-patterns/messaging/pgmq-queue-reconciliation).
  For ordered PGMQ work, choose `FifoHeads` as described in
  [typed PGMQ jobs](/docs/runtime-patterns/messaging/pgmq-jobs). Size the adapter's poll and ack
  retry budgets, choose the supervision strategy, and keep enqueues idempotent
  with [PGMQ connection faults and retry budgets](/docs/runtime-patterns/messaging/pgmq-connection-faults).

* **Implementing process coordination:** start with the
  [process-manager standard](/docs/runtime-patterns/messaging/process-managers); use
  [durable workflows](/docs/runtime-patterns/keiro/durable-workflows) when the work is a stable,
  journaled sequence rather than event-driven orchestration.

* **Inspecting subscription progress:** read the public
  [Kiroku durable checkpoint inventory](/docs/runtime-patterns/kiroku/checkpoint-inventory), keeping
  member rows and global-position distance distinct from live worker state and
  event lag.

* **Evolving persisted events:** follow
  [event-schema evolution](/docs/runtime-patterns/keiki/event-schema-evolution) for wire kinds,
  versions, defaults, and upcasters, then apply the
  [Keiro evolution gates](/docs/runtime-patterns/keiro/evolution-and-rollout), promoting advisories
  that must block a deploy with repeatable `diff --deny`.

* **Evolving database schemas:** follow
  [migration authoring](/docs/runtime-patterns/migrations/authoring), then use the
  [migration operations runbook](/docs/runtime-patterns/migrations/operations) for verification and
  repair. Keiro migration `0032` requires stopped timer writers before `up`.

* **Structuring packages and modules:** start with the
  [workspace-first service-contract standard](/docs/runtime-patterns/keiro/service-workspaces), then use the
  [service-package standard](/docs/runtime-patterns/architecture/service-packages) and
  [vertical-slice module standard](/docs/runtime-patterns/architecture/vertical-slice-modules). Satisfy
  [the generated compilation contract](/docs/runtime-patterns/architecture/generated-compilation-contract)
  when wiring the generated layer into Cabal, naming the runtime package, or
  building the generated conformance package.

* **Configuring a service:** begin with the
  [Settei service standard](/docs/runtime-patterns/config/settei-service-standard), and use the
  [Settei CLI standard](/docs/runtime-patterns/config/settei-cli-standard) for command-line tooling.

* **Operating Kubernetes:** follow the
  [Kubernetes deployment standard](/docs/runtime-patterns/config/kubernetes-deployment) for config,
  secrets, probes, and rollout behavior.

The [generated catalog index](https://github.com/shinzui/keiro-runtime-patterns/blob/master/runtime-patterns/index.md)
lists every subject and concept when you need exhaustive discovery.
